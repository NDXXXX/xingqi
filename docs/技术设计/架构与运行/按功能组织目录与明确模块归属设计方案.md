# 按功能组织目录与明确模块归属设计方案

## 文档状态

- 状态：实现完成；后续修复上下文摘要预算问题后，全量 Python 测试 289 项通过
- 目标：让开发者能按产品能力找到实现，并从目录判断模块归属和依赖方向。
- 实施方式：分批移动模块；每批有独立清单、依赖检查和回归范围。
- 范围：`src/zhiyu/` Python 源码的目录和导入路径；不改变产品行为、数据库结构、配置格式、用户数据和 Web 页面行为。
- 关联批次：[01 记忆域迁移](按功能组织目录与明确模块归属-01-记忆域.md)、[02 Agent 与模型能力迁移](按功能组织目录与明确模块归属-02-Agent与模型能力.md)、[03 渠道、集成与跨域流程迁移](按功能组织目录与明确模块归属-03-渠道集成与跨域流程.md)。

## 1. 问题与目标

当前实现按 `core`、`application`、`infrastructure` 等技术层分组，但同一项产品能力的入口、用例、核心实现、持久化适配分散在多个目录。`core` 还同时容纳 Agent、记忆、Provider、角色和工具等不同职责。开发者需要先猜技术层，再跨目录追踪同一功能；`application` 也逐渐成为所有产品能力的集合目录。

本方案按运行时职责组织顶层目录，而不是把所有代码继续按 `core/application/infrastructure` 技术层切开。功能目录拥有自己的服务、规则和专属工具；入口仍放在 `api/`、`cli/`、`channels/`；真正跨功能的流程仍由 `application/` 编排；SQL、配置、Repository 和 Migration 继续归 `infrastructure/`。

完成后应达到：

1. 按“Agent、对话、会话、记忆、模型、角色、渠道、MCP、Skills、定时任务”可以直接定位到唯一功能包。
2. 一个功能的业务服务、核心实现和专属工具不再散落于 `application/`、`core/`、`integrations/` 等多个同级技术层。
3. CLI、HTTP API 和渠道仍是适配入口，不能彼此调用来复用业务逻辑。
4. 持久化实现与数据库迁移仍集中在 `infrastructure/`。
5. 变更以纯移动和导入更新为主；外部行为、数据库和用户数据不变。

## 2. 目标目录

```text
src/zhiyu/
├── __main__.py                 # Python 模块入口
├── api/                        # FastAPI 应用、HTTP 路由和请求/响应模型
├── cli/                        # CLI、TUI 和命令适配
├── agents/                     # Agent 上下文、图、状态、运行管理及通用 Agent 工具
│   └── tools/                  # Agent 通用工具协议、实现和注册
├── chat/                       # 对话用例与 Agent 调用编排
├── sessions/                   # 会话历史、活跃运行控制和续接上下文
├── memory/                     # 记忆生命周期、检索、索引和记忆工具
│   └── index/                  # 索引共用逻辑、同步和重建
├── characters/                 # 角色服务和提示词
├── providers/                  # 对话模型、Embedding、路由和 Provider 服务
├── channels/                   # 通用消息、渠道运行时、QQ 适配和渠道服务
├── mcp/                        # MCP 连接、管理服务和协议适配
├── skills/                     # Skill 加载、生命周期、管理服务和 Agent 工具
├── scheduled_tasks/             # 定时任务服务、处理器和执行规则
├── application/                # 跨多个功能域的用例与运行时组装
├── infrastructure/             # 配置、密钥、数据库、Repository、Migration
├── web/                        # Python 侧静态资源挂载；构建产物不手改
└── core/                       # 仅保留已有的记忆索引兼容导入路径，禁止新增实现
```

目标不是把所有文件都塞进功能目录。`api/`、`cli/` 是外部适配入口；`application/` 保留确实跨域的工作流；`infrastructure/` 保留共享技术实现。目录名只在职责明确时新增，不为单文件建立空包或抽象层。

## 3. OpenClaw 目录组织的借鉴

对照 OpenClaw 当前 `main` 分支：它在 `src/` 下直接按运行时职责设目录，例如 `agents/`、`channels/`、`gateway/`、`memory/`、`sessions/`、`skills/`、`cron/`、`plugins/`、`llm/` 和 `infra/`。Agent Runtime 的设计文档又把 `src/agents/`、`src/llm/`、`packages/agent-core/` 的所有权逐项列出；渠道边界说明规定共享渠道代码与插件可见契约的边界。它不是单纯按“核心层/应用层/基础设施层”分组的大型 `core/` 包。参考：[OpenClaw 源码目录](https://github.com/openclaw/openclaw/tree/main/src)、[Agent Runtime 架构](https://github.com/openclaw/openclaw/blob/main/docs/agent-runtime-architecture.md)、[Agent 目录规则](https://github.com/openclaw/openclaw/blob/main/src/agents/AGENTS.md)、[Channels 边界规则](https://github.com/openclaw/openclaw/blob/main/src/channels/AGENTS.md)。

从它的分配方式借鉴四点：

1. **顶层目录表示责任所有者。** Agent Runtime、会话、记忆、渠道、Skills、MCP、调度等可以分别定位，不先猜技术层。
2. **子目录按子系统和运行生命周期拆分。** Agent 下再分 runtime、tools、sessions、sandbox 等；Channels 下再分消息、传输、入站事件、状态等。只有存在真实职责时才拆子目录。
3. **跨域组装和领域实现分开。** Gateway/Agent runtime 按明确边界组装能力，功能模块仍拥有各自状态与规则；避免用一个总 `application/` 文件夹接纳所有单域服务。
4. **目录边界配合文档约束。** OpenClaw 在关键源码目录放 `AGENTS.md` 写明所有权、调用边界与检查方式。星栖应先更新仓库根 `AGENTS.md` 的代码地图；只有某个子系统复杂到有独立规则时，再添加该目录说明，不复制大项目的文档数量。

星栖只借鉴这种“按运行时职责找代码”的办法，不复制 OpenClaw 的 Gateway、插件 SDK、`apps/`、`packages/` 或 `extensions/` 划分：星栖当前是单 Python 包、单机进程、React 前端和一个 QQ OneBot 适配器，没有对应的多应用工作区或第三方插件发布边界。保留 `api/`、`cli/`、`infrastructure/` 是基于现有产品形态，而不是照抄 OpenClaw 的目录名。

## 4. 模块归属和命名规则

| 代码类型 | 归属规则 | 示例 |
| --- | --- | --- |
| HTTP 路由、HTTP schema、CLI 命令 | 留在对应入口，负责协议转换、参数校验和结果呈现 | `api/routes/memories.py`、`cli/commands/memories.py` |
| 单一功能的对话与会话工作流 | 留在 `chat/`、`sessions/`；跨域参与不改变主责归属 | `chat/service.py`、`sessions/service.py` |
| 跨功能用例、运行时组装 | 留在 `application/`；该目录中的每个实现文件必须编排两个及以上功能，或负责应用级运行时生命周期。兼容策略列出的旧入口除外 | `application/runtime.py`、`application/data_archive.py` |
| 单一功能的服务、业务规则和专属 Agent 工具 | 放在对应顶层功能包 | `memory/service.py`、`skills/tool.py` |
| 通用 Agent 工具 | 放在 `agents/tools/`；不在这里放记忆、Skills 等专属工具 | `agents/tools/calculator.py` |
| 外部 Provider 协议实现 | 放在 `providers/`，按实现或协议命名 | `providers/anthropic.py`、`providers/openai_compatible.py` |
| 数据库、Repository、Migration、配置、密钥 | 放在 `infrastructure/`，SQL 不进入入口和功能服务 | `infrastructure/database/repositories/` |
| 独立扩展能力的连接、加载、协议细节 | 放在按能力命名的包；管理用例及专属 Agent 工具也归入对应能力包 | `mcp/`、`skills/` |

额外约束：

- 不再新增 `core/` 作为“其他核心代码”收纳目录；已有职责必须落入明确功能包。
- 不再新增只转发调用的 `Service`、`Manager`、`Registry` 或 `Factory`。已有 `MemoryService` 兼容门面按当前实现保留；本次不增加新门面。
- 功能包可以调用通用工具和基础设施适配。`infrastructure/` 不得依赖功能服务、入口或外部 SDK。允许使用无副作用的共享领域常量/纯函数，但必须与运行时实现分离：Provider 默认值放在 `providers/catalog.py`，不得让 Repository 导入会加载 SDK、密钥或 Provider 实现的路由模块；记忆共享范围判断放在纯规则模块。若后续要解除这些依赖，另立行为等价的变更并单独验证。
- `application/` 可以协调多个功能包，但功能包不反向导入 `application/`。
- 对单一功能的跨层实现采用同一顶层包，不以 `domain/`、`services/`、`repositories/` 等空泛层名再拆目录。
- 保持 Python 包边界明确：所有新包有 `__init__.py`；`__init__.py` 只导出确实需要的公共符号，不复制实现。
- 第 8 节列出的两个既有兼容入口是例外；新功能代码不得继续依赖这些旧路径。

## 5. 依赖方向

```text
CLI ─┐
API ─┼──> application（跨域用例 / 运行时组装） ──> 功能包
     │                                      └──> infrastructure
Channels ┘

功能包 ──> infrastructure（Repository、配置、数据库接口）
功能包之间：只允许有明确业务依赖；禁止循环依赖
infrastructure ──> 允许依赖无副作用共享领域常量/纯函数；禁止依赖服务、运行时实现、入口和外部 SDK
```

`application/runtime.py` 负责组装渠道运行时，因此可以引用 `channels/`；这是应用启动装配，不允许业务功能反向调用 CLI、API 或渠道入口。具体调用关系以每批迁移清单和现有实际调用为准，不因目录移动新增依赖。

## 6. 明确保留的位置

以下文件和目录不在本轮移动范围内，完整保留其现有相对路径：

- `src/zhiyu/__init__.py`、`src/zhiyu/__main__.py`：包元信息和模块入口。
- `src/zhiyu/api/**`：路由和 schema。路由继续调用 Application/功能服务，不直接放 SQL。
- `src/zhiyu/cli/**`：CLI/TUI 适配；命令按现有文件留在 `cli/commands/`。
- `src/zhiyu/infrastructure/**`：配置、密钥、数据库、全部 Repository 和 26 个 Alembic Migration。只更新其上游导入，不搬迁、不重命名 Migration；其中 `ProviderRepository` 只使用 `providers/catalog.py` 中与运行时实现分离的默认模型元数据，`MemoryRepository` 使用记忆共享范围纯规则。Repository 不得导入 Provider Router 或 Provider 实现。
- `src/zhiyu/web/**` 和 `web/src/**`：本次不调整前端组织。
- `src/zhiyu/web/static/react/**`：Vite 构建产物，不手动编辑。
- `tests/**` 和 `web/test/**`：测试按现有测试能力归属保留；导入路径同步更新，测试文件不随生产模块移动。
- 根级打包、README、配置文件：除确有旧导入路径需要更新外，不修改。

上述保留项避免把目录重组扩大成 API 设计、前端重构、数据库迁移或打包改造。若实施中发现打包配置显式列举了 `core` 路径，只做维持构建所需的最小同步。

每一批按以下步骤提交，禁止把三个批次堆成一个不可审查的大 diff：

1. 确认该批当前源文件、调用方、测试和公开导入面；若代码已与本方案清单不一致，先更新设计和清单。
2. 移动文件并同步所有仓库内导入、注解、动态导入、patch 路径和文档代码路径；一次提交内完成，避免半迁移状态。
3. 运行该批明确列出的测试，再运行类型/导入检查；检查旧路径是否仍被生产代码引用。
4. 检查 Git rename 识别、`git diff --check`、工作区状态和打包/CLI 入口。
5. 批次验收后再开始下一批；若发现需要行为修改，拆成单独修复提交并补充相应测试，不将其伪装成纯目录重组。

## 8. 公共导入兼容策略

已有后端可维护性设计明确要求保持 `MemoryService` 和索引器导入路径。本方案继承这项兼容约束：

- `zhiyu.application.memories.MemoryService` 保持兼容导入入口；实现可委托给 `zhiyu.memory.service`，旧文件只承担必要的导出和兼容职责。
- `zhiyu.core.memory.indexer` 保持兼容导入入口；索引实现归入 `zhiyu.memory`，旧模块只重导出既有公开函数。`core/` 最终因此只保留该兼容路径及包文件，不得在其中新增业务实现。
- 其余 `zhiyu.core.*` 路径按批次清单迁移。实施前仍须复核 README、`pyproject.toml`、发布说明和仓库外调用约定，确认没有其他稳定 Python 导入承诺。
- 对上述两项已有承诺以外的旧路径：若没有稳定 Python 导入 API 承诺，仓库内直接迁移，不保留空壳转发包；若确认存在外部消费者，则先修订本设计，明确兼容窗口和弃用版本。
- 不改变 CLI 命令、HTTP 路径/格式、数据库 schema、持久化文件路径和用户配置名。

## 9. 总体验收条件

所有批次完成后必须同时满足：

- 三份批次文档列出的每个移动项均迁移，保留项均留在原处；没有未解释的旧 `core/` 或单一功能服务散落在 `application/`。
- `src/zhiyu/core/` 不再包含业务实现；仅保留第 8 节明确的 `zhiyu.core.memory.indexer` 兼容入口及必要包文件。生产代码和测试统一导入新功能路径，兼容测试单独验证旧入口。
- `application/` 仅保留本设计明列的跨域工作流和运行时装配；新增文件需在代码注释或目录地图中说明跨域原因。
- 入口依赖方向符合第 4 节；无新循环导入、入口互调或 SQL 散落。
- Python 测试、CLI help、构建和数据库 Migration 检查通过；目录重组前后的用户可见行为一致。实施者在每批记录实际命令与结果，不预先声称通过。
- `AGENTS.md` 中代码地图与架构规则、`docs/README.md` 索引、必要的开发文档已同步；代码地图只描述实施完成后的实际结构。
- Git diff 能识别大部分文件重命名；无误删、无生成文件手改、无用户数据触碰。

本设计只定义目标和迁移验收，不表示任何批次已实施。
