# 多角色独立记忆设计方案

> 日期：2026-10-09  
> 状态：首版已实施（2026-10-09），验证与限制见第 11 节  
> 范围：在现有角色（Character）和记忆系统上增加多个可独立对话、各自记忆的 Agent。

## 1. 目标

用户可以自行创建任意多个智能体，为每个智能体设置名称和角色设定，再分别开始对话。每个智能体有自己的会话和长期记忆；一个智能体的记忆不会进入其他智能体的提示词、检索结果或记忆整理任务。底层继续共用现有 Provider、模型、工具和记忆实现。

本方案明确采用多 Agent：用户创建的每个智能体都是独立 Agent，有自己的 Agent ID、名称、角色设定、会话和记忆边界。它们可以共用同一份运行时代码、模型 Provider 和工具，但每轮调用都绑定一个确定的 Agent 身份；运行在同一个进程不代表它们是同一个 Agent。

首版不实现 Agent 之间自动委派、群聊或并行协作。这些属于多 Agent 之间的协作能力，不是拥有多个独立 Agent 的前提。首版也不增加 LangChain / LangGraph 依赖。

首版按以下范围设计：Web 是智能体创建和选择入口；现有默认助手继续保留；内置基础工具仍按现有策略提供，Skills 和 MCP 配置、启用状态及授权按 Agent 隔离。新建智能体不继承默认助手或其他 Agent 的 Skills / MCP。Skill 安装包可以共用一份文件，但必须分别关联到各 Agent；MCP 使用各 Agent 独立的配置、连接和授权。`Character.default_model_id` 仍可让智能体选用自己的默认模型。CLI / QQ 的 Agent 选择后续补齐。

目标行为：

1. 用户创建并选择智能体后，聊天使用该智能体的角色设定和默认模型。
2. 每个角色的 Conversation、摘要和长期记忆互相隔离。
3. 所有角色从空白记忆开始；当前已有记忆均为测试数据，可以在实施迁移中清除。保留角色、对话和消息数据。
4. 新产生的记忆归属于当前角色。首版不建立跨角色共享记忆，也不自动把一个角色的内容分享给其他角色。
5. 记忆的来源追踪、修改、遗忘、索引恢复和安全边界继续有效。

## 2. OpenClaw 参考点

OpenClaw 将 `agentId` 作为角色状态边界。每个 Agent 有自己的 workspace、人格与规则文件、状态目录和会话存储；内置记忆只检索该 Agent 自己的记忆。要让多个 Agent 读取同一份资料，需要显式配置共享路径。[多 Agent 文档](https://docs.openclaw.ai/multi-agent) · [Workspace 文档](https://docs.openclaw.ai/agent-workspace)

星栖借鉴这个边界和“默认隔离、显式共享”的规则，不复制 OpenClaw 的运行时、目录结构或插件机制。星栖已有角色提示词、Markdown 权威记忆、SQLite 索引和来源关系，沿用这些实现。

## 3. 实施前现状核对

- `characters` 表已有角色设定；`conversations.character_id` 绑定当前角色；`context.py` 将角色提示词加入 system prompt。
- 消息和摘要按 Conversation 保存，因此不同 Conversation 已有独立聊天历史。
- `Memory`、`MemoryJob`、记忆文件和召回目前按 `identity_id` 归属。`context.py` 取记忆时只传 `identity_id`，所以不同 Character 实际读同一份长期记忆。
- `MemoryManager` 的文件写入、自动提取、索引、晋升/合并和遗忘流程尚无 Character 维度。只在提示词中增加一个角色名称不能形成记忆隔离。

相关实现：[models.py](../src/zhiyu/infrastructure/database/models.py)、[context.py](../src/zhiyu/core/agent/context.py)、[memory_jobs.py](../src/zhiyu/application/memory_jobs.py)、[store.py](../src/zhiyu/core/memory/store.py)。

## 4. 核心模型与隔离规则

### 4.1 Character 是 Agent 身份

首版复用现有 `Character` 作为智能体配置，使用 `Character.id` 作为稳定的 Agent ID，不新增平行的 Agent、Workspace 或 Registry 实体。用户可以创建任意多个配置；名称、角色设定可修改，记忆归属使用 ID，不使用名称或目录名作为主键。产品界面称其为“智能体”，代码和现有 API 可继续使用 Character 命名。

智能体名称与角色设定使用现有 Character 字段（`name`、`description`、`personality`、`background`、`speaking_style`、`system_prompt`）；Conversation 绑定一个 Character；Memory 增加可空 `character_id`：

| `Memory.character_id` | 语义 | 可见范围 |
| --- | --- | --- |
| 当前角色 ID | 角色私有记忆 | 仅该角色 |
| `NULL` | 默认助手的记忆 | 仅无 Character 的默认助手会话 |

记忆查询同时限定 `identity_id` 和 Agent 范围。首版角色记忆不调用跨身份的 `shared` 记忆读取路径；现有 `Memory.shared` 字段语义不在本次扩展或复用。以后若要共享记忆，应另行设计明确的共享操作和可见范围。

### 4.2 空白初始化与身份

当前开发环境中的测试记忆数据可以清除：删除 `USER.md`、`IDENTITY.md`、`MEMORY.md`、`daily/`、`DREAMS.md` 等记忆内容，以及 Memory、索引、embedding、来源关系、待处理记忆任务和巩固状态。清理仅作用于当前已确认的测试数据，不放进会随版本发布的 Alembic 迁移；正式数据库迁移不得自动删除安装用户的记忆。保留 Conversation、Message、Character、Provider、模型和渠道配置。历史 Conversation 继续可读，但不会自动生成记忆归属或导入其历史内容。

每个新建智能体从空白记忆开始。名称以 `Character.name` 为准，角色设定由相应字段组成并注入该 Agent 的提示词；修改一个智能体的名称或角色设定只影响该 Agent，不修改其他智能体或默认助手身份。`AGENTS.md` 中的全局操作规则可以供所有 Agent 使用；默认助手的 `SOUL.md`、`BOOTSTRAP.md`、`IDENTITY.md`、`USER.md` 和记忆只供无 Character 的默认助手会话使用，不注入已绑定角色的会话。

新产生的记忆一律写入当前 Agent 空间。没有绑定 Character 的会话写入默认助手空间；选择角色的会话写入角色专属空间。角色间没有共享记忆读取或自动晋升。

### 4.3 会话归属

一个 Conversation 固定属于创建时选择的 Character。切换角色时创建或打开该角色的 Conversation，不把旧消息历史改挂到另一个角色。旧会话可继续通过会话列表访问。

如果用户在既有会话中改变角色，产品入口应转到目标角色的会话；底层不允许通过改 `conversation.character_id` 把历史记忆归属悄悄改掉。无角色的旧 Conversation 继续使用默认助手身份。

## 5. 数据与文件设计

### 5.1 数据库

使用 Alembic 增量迁移：

1. `memories` 增加 nullable `character_id`，外键指向 `characters.id`，并增加以 `(identity_id, character_id, status)` 为主的检索索引。
2. `memory_jobs` 增加 nullable `character_id`。创建后台提取任务时从 Conversation 快照角色 ID，Worker 使用快照写入记忆，防止排队期间角色设置变化导致写错空间。
3. 为 `conversations.character_id` 增加指向 `characters.id` 的保护性外键，防止删除角色后会话静默变成默认助手会话；迁移前将指向不存在角色的历史值置为 `NULL`，保留对应 Conversation 和 Message。
4. Character 删除时，首版禁止删除仍有关联会话或记忆的角色；用户需先显式删除其会话和记忆。不能依赖数据库级联静默删除记忆正文。
5. Conversation 已有关联，不新增 agent 表或重复保存角色名称。
6. MCP 配置增加可空 `character_id`，以 `(character_id, name)` 保证仅在同一个 Agent 作用域内唯一；`NULL` 属于默认助手。工具授权列表和连接状态随该配置隔离。已有 MCP 配置保留给默认助手，新建 Agent 不自动继承。
7. Skill 包仍由现有安装器维护，多个 Agent 可以引用同一安装包；新增 Agent 与 Skill 的显式关联表（例如 `character_skills`），默认无关联。默认助手保留现有启用状态；新 Agent 只读取其显式关联的 Skills。关联和启用状态分别记录，不在 Agent 之间继承；Skill 匹配与 `read_skill` 都按当前 Agent 过滤。

`MemorySource`、召回事件、embedding 和 Mutation Journal 通过 `memory_id` / `identity_id` 关联到记忆条目；在确认它们不需要独立的角色过滤后，不给每张表机械增加 `character_id`。所有通过这些表返回正文的查询，必须先经过带角色范围的 Memory 查询。记忆巩固调度须按 `(identity_id, character_id)` 分别取候选并运行，不能把同一身份下多个角色的候选放在一次晋升/合并处理中。

### 5.2 Skills 与 MCP 边界

- 每个 Agent 的工具注册表由内置基础工具、该 Agent 自己获授权的 MCP 工具和该 Agent 关联的 Skills 组成。
- Skill 文件可以由多个 Agent 引用同一安装包；授权关系不共享，单个 Agent 移除关联不会影响其他 Agent 的关联。
- `build_tool_registry` 不再把全局 MCP Manager 的所有工具和全局 Skill Registry 的所有 Skill 无条件加入角色会话。按 Conversation 的 Agent ID 查询配置，再生成本轮专属的过滤视图。
- MCP Server 的 tool/resource/prompt allowlist 继续使用现有最小权限规则，但配置归属于单个 Agent；Agent A 的 MCP 连接、密钥引用和授权不能被 Agent B 调用。
- Skill 是指导文档，不自动授予所需工具权限。只有分配给当前 Agent 且其 required tools 都在该 Agent 有效工具集中的 Skill 才能匹配或通过 `read_skill` 读取。
- 默认助手原有 MCP / Skill 配置迁移到默认助手作用域；不复制给新建 Agent。新 Agent 默认没有已启用的外部集成。

### 5.3 Markdown 目录

实施时复用现有 `Identity` 作为持久化记忆工作区：默认助手保留本地 Identity，每个 Character 对应独立的 `channel=agent` Identity，且 `Identity.id == Character.id`。Conversation、Memory、MemoryJob 同时绑定这个工作区与 Character。这样文件读写、索引、Mutation、恢复和巩固都沿用已实现的身份隔离，不再增加嵌套目录参数。

```text
memory/identities/
├── <local-identity-id>/    # 默认助手的文件空间
│   ├── USER.md
│   ├── MEMORY.md
│   ├── daily/
│   └── DREAMS.md
└── <character-id>/         # 当前智能体的独立工作区
    ├── MEMORY.md
    ├── daily/
    └── DREAMS.md
```

这是对原定 `identities/<identity-id>/agents/<character-id>/` 路径的实施调整，隔离目标相同。这里的 Identity 表示记忆工作区，不是新增用户账号或认证身份；CLI / QQ 的主人权限规则不变。

角色设定只由 Character 管理，不复制到 Markdown bootstrap 文件。Agent 提示词只注入自己的设定、记忆和默认空间的全局 `AGENTS.md` 规则，不注入默认助手的其他 bootstrap 内容。`Memory.file_path` 仍保存相对整个 memory 根目录的路径，索引和 Mutation 使用同一个完整工作区路径。

`identities.memory_reset_at` 记录清空边界：历史召回、后台提取及默认助手名字恢复忽略清空前的消息；排队或正在运行的提取、巩固任务在写回前复核边界，避免清空后恢复旧记忆。聊天记录仍保留，直接打开旧会话可继续查看原文。

## 6. 请求流程

### 6.1 创建智能体和选择会话

1. Web 智能体列表展示用户创建的 Character 配置，并提供创建、编辑和选择入口。
2. 开始新会话时将 `character_id` 写入 Conversation；恢复历史会话时以持久化的角色 ID 为准。
3. 聊天上下文组装器从 Conversation 取角色，并以 `(identity_id, character_id)` 查询记忆。
4. 提示词和本轮工具注册表都以 Conversation 的 Agent ID 组装：人格与记忆来自当前 Agent，Skills / MCP 只来自该 Agent 的授权配置；不注入默认助手的身份、记忆或集成。
5. 其他角色的记忆和会话摘要不能作为候选进入排序后再过滤；应在 SQL/文件来源范围处先隔离。

### 6.2 记忆写入

1. 入站消息创建 MemoryJob 时同时保存 `identity_id` 和 Conversation 的 `character_id`。
2. 后台抽取、晋升、合并均限制在该角色空间；不同角色之间不互相去重、覆盖或建立 supersedes 关系。
3. 自动抽取、纠正和晋升一律限制在当前角色空间；首版不提供跨角色共享写入。
4. 角色的记忆搜索/读取工具沿用现有工具实现，但工具构造时绑定当前身份和角色范围，不能接受模型传入任意角色 ID 扩大访问范围。
5. MCP 管理与 Skill 读取按 Agent scope 构建；模型不能通过传入另一个 Agent 的 ID 访问其连接、Skill 文件或授权。

### 6.3 修改、遗忘和恢复

- 记忆列表默认显示当前 Agent 自己的记忆，不提供跨角色共享切换。
- 编辑、完成、遗忘、恢复、巩固和索引修复按 `identity_id + character_id` 检查归属。
- 角色私有记忆不得通过只传 `identity_id` 的旧兼容方法被其他角色获取或修改。
- 角色删除和记忆空间删除必须经应用层明确处理；禁止只删除文件目录留下数据库缓存，或只删数据库行留下会被重建的 Markdown。

## 7. 实施分期

### 阶段零：移除待办和提醒

按用户决定移除现有待办/提醒功能，不把 `StandingIntent` 搬成 Agent 私有数据。删除范围包括对话中的提醒解析和注入、后台定时派发、提醒查询 API、Web 提醒提示、对应数据表及其测试和文档。此项是功能清理，不改变每个 Agent 的会话与记忆设计。

### 阶段一：持久化隔离和运行时召回

- 增加 Memory / MemoryJob 角色归属和迁移；MCP 配置与 Skill 关联按 Agent 隔离。
- 在当前开发数据目录单独清除已确认的测试记忆数据，保留会话原文但不自动导入；Alembic 迁移本身不删除记忆。
- 扩展仓储、MemoryStore、记忆索引和上下文组装，只读取当前 Agent 的记忆。
- 将自动记忆任务、工具、修复和恢复流程传入角色 ID。
- 自动提取的新记忆保存到当前角色；无角色时归默认助手。
- 角色会话不读取默认助手的 USER.md、IDENTITY.md 和旧记忆文件。

### 阶段二：产品入口

- Web 提供智能体的创建、编辑和选择入口，并让会话列表展示所属智能体。
- 选择智能体后创建该 Agent 的新会话；每个会话保持固定 Agent 归属。
- 智能体编辑页可单独配置 Skills 和 MCP；新 Agent 默认空授权，默认助手的旧配置只保留在默认助手。
- 记忆管理界面只展示当前角色的记忆，不提供共享操作。
- CLI / QQ 角色选择按各入口实际需求后续补齐；首版不要求所有入口同时支持创建角色。

### 阶段三：验证与数据维护

- 扩充来源图、巩固、删除、重建索引、身份共享与角色删除的回归覆盖。
- 提供按角色查看和清除记忆的管理入口。
- 根据实际使用再考虑 Agent 间委派或共享知识库；不预先设计其抽象。

## 8. 验收标准

1. 用户能够创建多个名称和角色设定各不相同的智能体，并在聊天入口分别选择。
2. 一个智能体对话中生成的记忆可在该智能体后续新会话召回，在其他智能体上下文、memory search/get 工具和巩固输入中均不可见。
3. 新建智能体的记忆初始为空；各自新产生的记忆只由所属智能体召回。
4. 新 Agent 默认看不到其他 Agent 的 Skill 或 MCP 工具；显式为不同 Agent 分别配置后，访问授权仍然独立。
5. 当前开发环境的测试记忆清理保留 Conversation 和 Message；正式 Alembic 迁移不删除已安装用户的记忆；之后的来源会话、消息、修改、遗忘和恢复操作有效。
6. 后台任务排队期间切换到其他角色，不会导致记忆写入到错误空间。
7. 记忆文件索引可以按身份和角色增量同步、重建；外部编辑、Mutation Journal 恢复和文件权威规则保持一致。
8. Web/CLI/QQ 入口共享 Application/Core 业务，不互相调用入口代码；写请求安全检查、QQ 主人/白名单校验保持不变。

## 9. 与现有设计文档的关系

- [角色系统设计方案](角色系统设计方案.md)定义 Character 的创建和提示词，继续有效；本方案补上记忆归属和前端选择体验。
- [星栖对齐 OpenClaw 记忆机制设计方案](星栖对齐OpenClaw记忆机制设计方案.md)和[单机个人 Agent 多 Session 共享记忆设计方案](单机个人Agent多Session共享记忆设计方案.md)描述现有的身份级记忆行为。本方案新增 Agent 级隔离；同一 Character 的多个 Session 共享该角色记忆，不同 Character 默认隔离。角色绑定的会话不再读取身份根目录中的默认助手记忆。
- 若前述文档中“单个 Agent 只有一个记忆空间”的表述被理解为整个应用全局唯一，与本方案的多角色目标冲突。进入实施时应以本方案的角色级隔离规则为准，并只更新冲突段落，避免重写已经完成的记忆架构决策。

## 10. 主要风险与约束

- 记忆生命周期涉及文件、SQLite 索引、Mutation、来源图和后台任务；只改召回 SQL 会造成错误写入或恢复后串记忆，阶段一必须完整贯通写入到遗忘链路。
- 当前开发环境的测试数据清理会保留完整聊天记录。正式 Alembic 迁移不删除用户记忆；记忆提取仅处理启用 Agent 记忆后的新对话，不回填旧消息。
- 用户身份与 Agent 角色是不同维度。所有查询必须同时校验 `identity_id`，不能只按 `character_id` 暴露私有数据。
- 角色删除和记忆清除都可能改变可见范围，应通过应用层操作并留下可审计来源，不让模型自行改变权限。
- 待办和提醒按用户决定从产品移除；不增加 `StandingIntent.character_id`，也不在 Agent 之间迁移提醒。
