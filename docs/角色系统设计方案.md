# 角色（Character）系统设计方案

> 版本：v1.1  
> 日期：2026-09-29  
> 状态：已实施  
> 定位：CLI 优先阶段第 1 步，补齐角色能力的创建入口  
> 上游文档：[CLI 优先开发设计方案](CLI优先开发设计方案.md)

## 1. 结论

角色能力的**读取和绑定已经可用，只有"创建"没有入口**，导致整条链路实际不可用。

本方案不新增 Agent 能力，只做三件事：

1. 增加 `zhiyu character` 命令组，补上创建、查看、删除入口。
2. 修正交互式聊天中 `/character` 的行为，使其与[上游文档 §5.2](CLI优先开发设计方案.md) 的规划一致。
3. 把角色读写从 CLI 收进应用服务，符合[上游文档 §3.1](CLI优先开发设计方案.md) 的分层约束。

验收方式：能通过 CLI 建出一个角色，在聊天里切换后模型口吻确实改变。

## 2. 现状核查

角色链路分三段，前两段通、第三段断。

### 2.1 读取（已通）

| 位置 | 行为 |
|---|---|
| [context.py:31](../src/zhiyu/core/agent/context.py#L31) | 会话绑定角色时，取角色拼成 system prompt |
| [selection.py:54](../src/zhiyu/core/providers/selection.py#L54) | 角色可指定默认 Provider |
| [selection.py:73](../src/zhiyu/core/providers/selection.py#L73) | 角色可指定默认模型 |
| [prompts.py](../src/zhiyu/core/characters/prompts.py) | 有 `system_prompt` 用自定义，否则按字段拼接 persona |

### 2.2 绑定（已通）

[main.py:105](../src/zhiyu/cli/main.py#L105) 的 `_set_character` 校验角色存在后写入 `conversation.character_id`。

### 2.3 创建（断裂）

[CharacterRepository](../src/zhiyu/infrastructure/database/repositories/character_repository.py) 的增删改查四件套完整，但 `create` **全项目只有测试调用过一次**（[test_agent_context.py:27](../tests/test_agent_context.py#L27)），产品代码没有任何调用点。全部四个产品侧引用都只调用 `get`：

| 位置 | 调用 |
|---|---|
| [context.py:16](../src/zhiyu/core/agent/context.py#L16) | 模块级实例，仅 `get` |
| [selection.py:54](../src/zhiyu/core/providers/selection.py#L54) | 仅 `get` |
| [selection.py:73](../src/zhiyu/core/providers/selection.py#L73) | 仅 `get` |
| [main.py:110](../src/zhiyu/cli/main.py#L110) | 仅 `get` |

数据库迁移没有种子数据，也没有其他写入路径。结论：

- `characters` 表永远是空的。
- `/character <id>` 永远找不到合法 ID。
- 角色能力对用户**完全不可达**——不是缺一个列表，是缺入口。

### 2.4 设计上的遗漏

[上游文档 §5.2](CLI优先开发设计方案.md) 规划了 `/character` 显示当前角色和 `/character <id>` 切换角色，但 §5.3 的后续调试命令列表里没有任何 `character` 命令。创建入口从未被规划，这是设计阶段的遗漏，本方案补上。

### 2.5 顺带发现的缺陷

[main.py:161](../src/zhiyu/cli/main.py#L161) 的判断是 `text.startswith("/character ")`，注意**空格**。因此裸输入 `/character` 会落到 [main.py:175](../src/zhiyu/cli/main.py#L175) 的"未知命令"分支，与 §5.2 规划的"显示当前角色"不符。

## 3. 命令设计

### 3.1 命令组

```bash
zhiyu character list
zhiyu character show <id>
zhiyu character add --name <name> [字段选项]
zhiyu character delete <id>
```

与现有 `provider`、`qq` 保持一致：嵌套子解析器、`required=True`、kebab-case 选项名。

### 3.2 `character add` 参数

| 选项 | 对应字段 | 必填 |
|---|---|---|
| `--name` | `name` | 是 |
| `--description` | `description` | 否 |
| `--personality` | `personality` | 否 |
| `--background` | `background` | 否 |
| `--speaking-style` | `speaking_style` | 否 |
| `--system-prompt` | `system_prompt` | 否 |

只做选项输入，不做交互式问答。理由：上游 §5 已明确"第一版 CLI 面向开发调试"，选项形式可脚本化、可测试、无隐藏状态；逐项问答的体验交给后续 Web UI 的表单承担。

**优先级陷阱**：`build_system_prompt` 在 `system_prompt` 非空时**完全忽略其他字段**。同时传入时 CLI 必须打印提示，避免用户以为 `--personality` 也生效了。

### 3.3 示例

```bash
zhiyu character add --name Luna --personality 温柔 --speaking-style 简短口语
zhiyu character list
zhiyu character show 3f2a...
zhiyu character delete 3f2a...
```

## 4. 交互式命令调整

对齐[上游 §5.2](CLI优先开发设计方案.md)：

| 输入 | 行为 | 现状 |
|---|---|---|
| `/character` | 显示当前角色名与摘要；未绑定则提示 | ❌ 报"未知命令"，需修 |
| `/character <id>` | 切换到指定角色；ID 不存在时报错 | ✅ 已实现 |

`/help` 的帮助文本（[main.py:144](../src/zhiyu/cli/main.py#L144)）同步补上裸 `/character`。

`/character <id>` 需要用户知道 ID，由 `character list` 提供。这是引入 `list` 的直接理由。

## 5. 应用服务与分层

上游 §3.1 要求 CLI 只负责参数解析和展示。当前 [main.py:105](../src/zhiyu/cli/main.py#L105) 的 `_set_character` 直接用 `SessionLocal` 和两个仓储，属于分层例外。本方案一并收敛。

新增 `src/zhiyu/application/characters.py`：

```python
class CharacterService:
    def list(self) -> list[CharacterSummary]: ...
    def get(self, character_id: str) -> CharacterSummary | None: ...
    def create(self, *, name: str, **fields) -> CharacterSummary: ...
    def delete(self, character_id: str) -> None: ...
    def current_for_conversation(self, conversation_id: str) -> CharacterSummary | None: ...
    def assign_to_conversation(self, conversation_id: str, character_id: str) -> None: ...
```

对外返回 `CharacterSummary` 而非 ORM 对象，避免会话关闭后访问未加载属性。`current_for_conversation` 是 §4「显示当前角色」所需的读取入口，与 `assign_to_conversation` 成对，两者都放在服务内以免 CLI 直接接触 `ConversationRepository`。

与 `ProviderService`、`ChannelService`、`ChatService` 同级，构造参数接受 `session_factory`，便于测试注入内存数据库。

CLI 侧 `_character(args)` 只做参数转接与结果打印；`_set_character` 改为调用 `assign_to_conversation`。

角色不存在时 `assign_to_conversation` 抛 `ValueError`，由 [main.py:290](../src/zhiyu/cli/main.py#L290) 既有的 `except ValueError` 分支统一转成退出码 2，不新增错误处理路径。

## 6. 输出格式

第一批只做人类可读输出，`--json` 按[上游 §5.3](CLI优先开发设计方案.md) 在后续统一补充。

`list` 必须输出完整 ID。角色切换只接受精确 ID，而 `CharacterRepository.get` 不做前缀匹配，输出短 ID 会让 `/character <id>` 无法使用：

```text
$ zhiyu character list
Luna [cb0046bf-ab56-4aa7-91c6-dd5a9277429f] 温柔 · 简短口语
小玉 [260fb396-6f5f-4389-b8f3-2ae2e475d419] 古风 · 系统提示词已覆盖
```

`add` 同样回显完整 ID，否则无法立即调用 `/character <id>`：

```text
$ zhiyu character add --name Luna --personality 温柔
已创建 Luna (cb0046bf-ab56-4aa7-91c6-dd5a9277429f)
```

## 8. 验收标准

手动验收（每条都可执行）：

```bash
zhiyu character list                          # 空库时给出明确提示，不报错
zhiyu character add --name Luna --personality 温柔
zhiyu character list                          # 能看到 Luna
zhiyu chat                                    # 交互模式
  /character                                  # 未绑定：提示尚未选择角色
  你好                                        # 先建会话
  /character <上一步的 ID>                     # 切换成功
  你是谁                                      # 回复口吻体现"温柔"
  /character                                  # 显示当前为 Luna
```

必须同时满足：

1. `uv run pytest -q` 全绿。
2. 上述序列逐步可复现，无异常退出。
3. 切换角色前后，同一条提问的回复风格有可观察差异。
4. 角色不存在时给出可读错误，退出码 2，不打印堆栈（`--debug` 除外）。

### 8.1 实施结果

验证时使用 `ZHIYU_DATA_DIR` 指向临时目录，未触碰真实数据。

| 项 | 结果 |
|---|---|
| 1 | 通过，65 项测试全绿（新增 9 项服务测试、4 项 CLI 测试） |
| 2 | 通过，`list` / `add` / `show` / `delete` / 裸 `/character` / `/character <id>` 全部实测 |
| 3 | **未验证**。需要已配置 Provider 与可用 API Key，验证环境不具备 |
| 4 | 通过，`show` 与 `delete` 传不存在的 ID 均输出 `配置错误：角色不存在`，退出码 2 |

第 3 项之外，角色注入链路已用 `with_agent_context` 单独确认：切换后会话的 system prompt 从空变为 `你是Luna。\n性格：温柔\n说话风格：简短口语`。即"角色是否生效"已验证，"模型是否据此改变口吻"待有 Key 时人工确认。

## 9. 范围边界

明确不在本次实施：

| 不做 | 理由 |
|---|---|
| `character update` | 有 `delete` + `add` 即可修正；改字段的需求尚未出现 |
| `--default-model` | `default_model_id` 存的是 `ModelConfig.id`，但 `provider list` 只打印模型名，CLI 无法让用户拿到 ID。且同名模型可能存在于多个 Provider，需要 `--provider` 配合，属于单独一步 |
| `--avatar` | 只存路径或 URL，CLI 无展示场景 |
| 交互式问答创建 | 交给 Web UI 表单 |
| `--json` | 按上游 §5.3 统一补充 |
| 角色文件导入（Markdown/YAML） | 需求未出现 |
| 修改 `default_model_id` 的模型选择逻辑 | 现有 selection 逻辑不动 |

`default_model_id` 字段在本次实施后仍无写入入口，保持现状并在下一阶段与 `provider list` 输出一起处理。

## 10. 后续步骤

本方案只覆盖第 1 步。后续顺序与理由：

| 顺序 | 内容 | 为什么排这个位置 |
|---|---|---|
| 1 | **角色创建入口**（本方案） | 链路断得最彻底，且底层已就绪，改动最小 |
| 2 | Memory 可见性（`memory list` / `forget`） | 抽取已在聊天中自动运行，但完全不可观察，风险高于角色 |
| 3 | `conversation list` | 补上 `--conversation` 需要预先知道 ID 的缺口，工作量小，可并入 1 或 2 |
| 4 | Skills、MCP 调试命令 | 属于接入外部能力，先确保自身核心链路可验证 |

2、3、4 的命名已在[上游 §5.3](CLI优先开发设计方案.md) 规划，实施时另开方案。
