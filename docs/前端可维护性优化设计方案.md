# 前端可维护性优化设计方案

## 目标

逐步降低前端修改的定位成本和回归风险。一次只整理一个功能域，保持现有页面表现、接口路径和用户操作不变；以功能边界组织代码，不为抽象而抽象。

## 当前问题

`web/src/app.tsx` 同时承载应用外壳、导航、跨页面状态、API 加载、聊天流控制，以及八个页面的界面。页面数据加载集中在同一个 `useEffect` 中，页面 JSX 则以 `renderX` 闭包形式放在 `App` 函数里。因而改动一个页面时，开发者需要在这个大组件里同时追踪状态、加载和显示逻辑。

记忆页是一个明确的拆分边界：搜索条件、记忆列表、巩固记录、加载状态和记忆操作只服务于记忆页面。聊天页也有清楚的显示边界；聊天流的生命周期与应用导航状态有关，第一步只拆显示组件，后续再单独评估是否把流控制提取成 Hook。

## 设计原则

1. 页面拥有只服务于自己的数据状态和加载逻辑。
2. `App` 负责应用级外壳、导航、最近会话和需要跨页面共享的聊天生命周期。
3. 公共 API 请求和小型通用展示组件集中复用；页面专属逻辑留在页面目录。
4. 每次迁移保持接口和交互行为不变，完成一个功能域后再迁移下一个。
5. 不提前引入路由框架、全局状态库、通用数据获取层或新的 UI 抽象。

## 目标目录

```text
web/src/
  app.tsx                    # 应用外壳、导航、跨页面协调
  api.ts                     # 统一 request/post 与 API 错误处理
  format.ts                  # 通用日期/列表格式化
  types.ts                   # 页面共享的基础类型
  hooks/
    useChatSession.ts        # 聊天流、取消和消息生命周期
  components/
    StateCard.tsx            # 空状态与错误状态展示
  pages/
    ChatPage.tsx             # 聊天界面
    MemoryPage.tsx           # 记忆查询、记忆列表和记忆操作
    OverviewPage.tsx         # 运行总览
    ProvidersPage.tsx        # Provider 管理
    ChannelsPage.tsx         # QQ 渠道
    McpPage.tsx              # MCP 管理
    SkillsPage.tsx           # Skills 管理
    DiagnosticsPage.tsx     # 渠道诊断
```

各页面组件负责自己的展示和页面数据加载；`App` 负责应用外壳及跨页面协调。

## 分阶段方案

### 第一阶段：拆分聊天与记忆页面（已完成）

- 将公共 JSON 请求和 HTTP 方法选项放入 `api.ts`。
- 将空状态组件提取到 `components/StateCard.tsx`。
- 将聊天视觉界面放入 `pages/ChatPage.tsx`。聊天流控制随后迁入 `useChatSession`。
- 将记忆页放入 `pages/MemoryPage.tsx`，由页面组件管理搜索条件、记忆与巩固记录加载、错误/加载显示，以及确认、保留、纠正、删除操作。
- 从 `App` 移除记忆页专属状态和记忆数据加载分支。

### 第二阶段：拆分聊天生命周期（已完成）

- `sendMessage`、SSE 事件解析、取消和消息更新由 `useChatSession` 管理。
- 最近会话列表和 URL 导航由 `App` 协调。

### 第三阶段：逐页迁移管理页面（已完成）

- 总览、Provider、QQ 渠道、MCP、Skills 和诊断页面已迁入独立模块。
- 管理页在各自模块加载并持有页面数据和加载状态。
- Provider 模型配置与 MCP 授权、连接和凭据操作已随页面迁移。
- 顶部新增 Provider、MCP、Skill 的动作仍由 `App` 传入页面，保留统一标题栏。
- 页面通过 `reloadKey` 响应顶部刷新；加载失败时使用统一错误状态和重试入口。

## 验收标准

- 所有页面 JSX 不再定义在 `app.tsx`；`app.tsx` 保留应用外壳、导航、最近会话和跨页面协调。
- 聊天生命周期由 `useChatSession` 管理；管理页各自持有数据加载和页面状态。
- 记忆搜索、层级筛选、巩固记录、确认、保留、纠正、删除仍调用原有 API，并在操作后刷新当前结果。
- 顶部刷新按钮仍能触发当前记忆页面重新加载。
- 错误和空状态仍有可理解的提示及重试入口。
- 不改变视觉样式、API 路径或数据格式。

## 风险与处理

- 页面拆分容易遗漏回调或改变加载时机：沿用原请求路径和依赖关系，并逐项对照页面操作。
- 页面卸载时请求可能返回：记忆页加载使用清理标志，卸载后不再更新状态。

## 验证

本次前端类型检查和生产构建通过；没有运行测试。后续页面行为修改应运行现有前端测试，并检查聊天流、记忆操作及各管理页加载和刷新。
