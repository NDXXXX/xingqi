# Desktop AI Companion 设计文档 v2

## 1. 文档目标

本文档基于当前已经可以运行的 MVP，定义下一阶段的稳定化与产品化方案。

当前项目已经具备：

- Electron 桌面端
- FastAPI 本地 Agent Runtime
- 多模型 Provider
- 流式对话与工具调用
- Conversation / Message 持久化
- Character、Memory、Skills
- MCP
- QQ OneBot 渠道

v2 不重写现有项目，重点解决以下问题：

1. Provider 配置只能新增，无法完整管理。
2. SQLite 没有数据库迁移机制。
3. QQ、MCP 配置重启后丢失。
4. Memory 没有按身份隔离。
5. Agent 流式与非流式执行逻辑重复。
6. 前端错误反馈、运行状态和自动化测试不足。
7. 桌面应用缺少正式打包与升级方案。

---

## 2. 设计原则

### 2.1 本地优先

默认将数据保存在用户电脑中，不依赖云端账户。

### 2.2 敏感信息不进入数据库

API Key、QQ Access Token 等敏感信息只保存到系统钥匙串，SQLite 只保存引用。

### 2.3 单 Agent 保持简单

v2 继续使用单 Agent，不引入 Multi-Agent、复杂任务编排和分布式服务。

### 2.4 所有渠道共享能力

Desktop 和 QQ 必须共享：

- Provider
- Character
- Memory
- Skills
- 内置 Tool
- MCP Tool

### 2.5 改动必须可迁移

已有数据库和会话数据不能因为升级而丢失。

### 5.1 后端分层

## 6. 数据库迁移

### 6.1 技术方案

使用 Alembic 管理数据库版本。

```text
apps/server/
├── alembic.ini
├── migrations/
│   ├── env.py
│   └── versions/
└── app/database/
```

启动流程：

```text
启动 Backend
→ 获取数据库文件锁
→ 执行 alembic upgrade head
→ 启动 FastAPI
```

### 6.2 迁移要求

- 首个 migration 必须兼容现有数据库。
- 迁移前不删除用户数据。
- 破坏性迁移必须先备份数据库。
- 开发和生产使用同一套 migration。
- 禁止继续使用 `create_all()` 作为正式升级机制。

## 8. 统一 Agent Runtime

### 8.1 当前问题

流式和非流式分别维护执行循环，可能导致：

- 工具调用行为不一致
- 最大轮数不一致
- 错误处理不一致
- 新增 Agent 事件需要修改两处

### 8.2 统一事件模型

Agent Core 只维护一个执行循环，并输出事件：

```python
AgentEvent = (
    RunStarted
    | StepStarted
    | TextDelta
    | ToolCallStarted
    | ToolCallFinished
    | StepFinished
    | RunCompleted
    | RunFailed
)
```

非流式接口消费全部事件后返回最终结果；SSE 接口收到事件后立即转发。

```text
Agent Core
    │
    ├── collect all → POST /api/chat
    │
    └── forward each → POST /api/chat/stream
```

### 8.3 取消执行

每次运行生成 `run_id`，保存对应的取消信号。

```text
POST /api/chat/stream
DELETE /api/agent/runs/{run_id}
```

客户端断开 SSE 时，后端也应取消：

- Provider HTTP 请求
- 正在执行的 Tool
- MCP Tool 调用
- 后续 Memory Extraction

### 8.4 超时

建议默认值：

```text
Provider 请求       60 秒
内置 Tool           15 秒
MCP Tool            30 秒
单次 Agent Run      180 秒
最大工具调用轮数     10
```

## 10. Identity 与 Memory 隔离

### 10.1 Identity 数据模型

```text
Identity
├── id
├── channel             desktop / qq
├── external_user_id
├── display_name        nullable
├── created_at
└── updated_at
```

唯一约束：

```text
(channel, external_user_id)
```

Conversation 增加：

```text
identity_id
```

Memory 使用：

```text
identity_id
```

替换目前含义不明确的 `user_id`。

### 10.2 检索范围

```text
当前 Identity 的 Memory
+ 标记为 shared 的 Memory
```

默认禁止跨 QQ 用户检索记忆。

### 10.3 桌面身份

首次启动时创建一个固定的本地 Identity：

```text
channel = desktop
external_user_id = local-user
```

## 12. MCP

### 12.1 持久化模型

```text
McpServerConfig
├── id
├── name                UNIQUE
├── command
├── args_json
├── env_refs_json
├── enabled
├── auto_connect
├── created_at
└── updated_at
```

环境变量中的秘密值保存至 Keychain，数据库只保存引用。

### 12.2 生命周期

```text
Backend 启动
→ 加载 auto_connect 配置
→ 并行连接 MCP Server
→ 注册工具
→ 发布连接状态

Backend 关闭
→ 停止接收新调用
→ 等待或取消正在运行的调用
→ 关闭 MCP Connection
```

### 12.3 工具命名冲突

MCP 工具使用命名空间：

```text
{server_name}.{tool_name}
```

例如：

```text
filesystem.read_file
github.create_issue
```

禁止 MCP 工具覆盖内置工具。

## 13. Conversation 与 Chat

### 13.1 Conversation 功能

- 新建
- 删除
- 重命名
- 搜索
- 按更新时间排序
- 显示渠道来源
- 保存上次使用的模型和 Character

新增 API：

```text
PATCH /api/conversations/{id}

{
  "title": "新的标题",
  "character_id": "...",
  "model_id": "..."
}
```

### 13.2 Regenerate

重新生成不应重复创建用户消息。

流程：

```text
找到最后一条 user message
→ 删除或归档其后的 assistant message
→ 使用原上下文重新运行 Agent
→ 写入新的 assistant message
```

API：

```text
POST /api/conversations/{id}/regenerate
```

### 13.3 消息状态

前端临时消息增加状态：

```text
sending
streaming
completed
failed
cancelled
```

失败消息提供“重试”操作。

### 13.4 上下文裁剪

Provider 请求前根据模型上下文窗口裁剪历史：

```text
System Context
+ 最近相关 Memory
+ 匹配 Skill
+ 最近 N 条 Conversation Message
```

System Context 不允许被历史消息裁剪掉。

## 14. 前端状态管理

### 14.1 Store 拆分

当前单一 Store 后续可按领域拆分：

```text
conversationStore
chatStore
providerStore
characterStore
memoryStore
integrationStore
uiStore
```

只有当单一 Store 已明显影响维护时再拆分，不提前建立复杂抽象。

### 14.2 通用异步状态

每个操作统一维护：

```typescript
type AsyncStatus = 'idle' | 'loading' | 'success' | 'error'
```

错误信息通过统一 Toast 展示，表单字段错误仍显示在字段附近。

### 14.3 响应式布局

```text
宽屏：Sidebar + Chat + Agent Run
中屏：Sidebar + Chat，Agent Run 可抽屉打开
窄屏：单页面，Sidebar 与 Agent Run 均使用抽屉
```

### 14.4 可访问性

- 所有输入框具有关联 Label。
- Icon Button 必须有 `aria-label`。
- 错误使用 `role="alert"`。
- 动态状态使用 `aria-live`。
- 所有交互支持键盘操作。
- 焦点状态必须可见。

## 15. 错误处理

### 15.1 标准错误响应

```json
{
  "error": {
    "code": "PROVIDER_AUTH_FAILED",
    "message": "API Key 无效",
    "retryable": false,
    "request_id": "..."
  }
}
```

### 15.2 错误分类

```text
VALIDATION_ERROR
NOT_FOUND
CONFLICT
PROVIDER_AUTH_FAILED
PROVIDER_RATE_LIMITED
PROVIDER_UNAVAILABLE
TOOL_EXECUTION_FAILED
MCP_CONNECTION_FAILED
CHANNEL_CONNECTION_FAILED
RUN_CANCELLED
INTERNAL_ERROR
```

### 15.3 日志要求

- 每个请求生成 `request_id`。
- 每次 Agent 执行生成 `run_id`。
- 禁止记录 API Key 和 Access Token。
- Provider 响应只记录必要元数据。
- 日志默认写入本地滚动文件。

## 16. 安全

### 16.1 API 边界

FastAPI 仅监听：

```text
127.0.0.1
```

生产模式不使用 `allow_origins=["*"]`，改为允许桌面应用来源，并增加随机启动 Token 防止其他本地网页调用。

### 16.2 命令执行

MCP Server 启动属于本地命令执行能力，因此：

- UI 明确展示最终 command 和 args。
- 首次连接要求用户确认。
- 不通过 shell 拼接执行。
- 环境变量使用白名单传递。
- 日志中隐藏秘密值。

### 16.3 Markdown

- 禁止直接渲染不可信 HTML。
- 外部链接使用安全打开方式。
- 不允许模型消息执行脚本。
