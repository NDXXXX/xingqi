# 记忆系统改进设计方案

> 版本：v1.0  
> 日期：2026-10-01  
> 状态：A～D 阶段已实施  
> 定位：CLI 优先阶段，提升长期记忆的准确性、可维护性和召回质量  
> 上游文档：[CLI 优先开发设计方案](CLI优先开发设计方案.md)

## 1. 目标与范围

让用户能感受到三件事：稳定信息能被记住，改口能覆盖旧信息，误记能被查看和纠正。

设计假设：继续使用当前 Python 应用分层、SQLAlchemy 和默认 SQLite 数据库；本地用户继续共用 `local` 身份，外部渠道沿用现有身份解析。本方案不改变渠道身份模型。

A、B 阶段完成正确性与管理入口，C 阶段调整检索，D 阶段加入可恢复的后台提取。四个阶段均已实施。

本次不引入向量数据库、知识图谱、自动历史回填或模型生成的整段会话摘要。embedding 是否需要引入，由检索评估结果决定。

## 2. 实施前基线与问题

以下表格保留实施前的基线，用于说明本次改造解决的问题；后续章节描述当前已落地行为。

| 环节 | 当前实现 | 问题 |
|---|---|---|
| 提取 | 回答后使用同一 Provider 和模型，读取本轮用户消息与助手回答 | 未明确区分事实来源，助手建议可能被误记 |
| 去重 | 相同或互为子串就跳过 | 可能丢掉否定、补充与纠正信息 |
| 写入 | 只新增记录 | 无法替换旧偏好、完成目标或撤销事实 |
| 存储 | `memories` 表，包含类型、内容、身份、共享标记、重要性 | 无来源和生命周期 |
| 检索 | 字符 bigram 重叠数量乘重要性，取前 5 条 | 同义表达漏召回，长文本可能占优 |
| 隔离 | 指定身份时读取该身份及共享记忆 | 身份为空时读取全部记录 |
| 恢复 | 新本地会话注入上次会话末尾 6 条消息及所有目标/项目 | 已完成目标仍被当作进行中事项 |
| 可观察性 | 仓储支持 CRUD，CLI 没有记忆命令 | 用户无法核查或纠正 |

## 3. 预期行为

| 用户输入 | 预期操作 | 后续行为 |
|---|---|---|
| 我喜欢咖啡 | 新增 `preference` | 相关建议可使用该偏好 |
| 最近戒咖啡了，以后别推荐 | 替换旧偏好 | 只使用新的有效偏好 |
| 我喜欢咖啡，也喜欢茶 | 新增另一条偏好 | 两条信息并存 |
| MCP 接入已经完成 | 完成匹配的目标/项目 | 欢迎与召回不再显示它进行中 |
| 刚才说错了，我不在北京 | 使旧事实失效 | 不推断用户的新住址 |
| 助手说：你可以考虑学 Rust | 不保存用户目标 | 建议不等于用户承诺 |
| 小说人物说：我住在北京 | 不保存用户事实 | 引用和角色扮演不进入用户档案 |

用户明确的长期自述可以保存；猜测、临时闲聊、引用、工具输出和助手建议不能直接作为用户事实。遇到否定或冲突时，以用户最新明确表达为准；指代或目标匹配不清楚时，不自动修改旧记录。

## 4. 数据结构与生命周期

保留现有字段，增加以下字段：

| 字段 | 类型 | 用途 |
|---|---|---|
| `status` | 字符串，非空，默认 `active` | `active / completed / superseded / invalidated` |
| `source_message_id` | 可空，外键指向 `messages.id` | 创建本条记忆的用户消息 |
| `status_source_message_id` | 可空，外键指向 `messages.id` | 导致完成、替换或失效的用户消息 |
| `supersedes_id` | 可空，自引用外键 | 新记忆替换的旧记忆 |
| `origin` | 字符串，非空 | `automatic / manual / legacy` |

来源外键使用 `ON DELETE SET NULL`：删除会话不会连带删除长期记忆；详情页显示“来源消息已删除”。记忆来源仍存在时，详情页展示消息和所属会话。

不新增置信度或有效期字段。当前模型无法提供经过校准的置信度，过期规则也缺乏产品依据。

生命周期：

```text
新增 → active
替换 → 旧记录 superseded + 新记录 active
完成 → completed（仅 goal/project）
撤销事实 → invalidated
用户忘记 → 物理删除指定记录
```

替换时保留旧内容用于核查，并建立新旧关系。第一版不提供自动恢复完成事项；用户重新开始目标时创建新的有效记录。

`importance` 保留，自动创建继续使用 0.5，不让提取器自行调分。对重要性的调整留待召回评估后决定。

### 4.1 迁移

1. 新建 Alembic 迁移，版本号接在当前迁移链末尾。
2. 旧记录设为 `status=active`、`origin=legacy`，来源与替换关系为空。
3. 核查残留的空身份记录；无法确定归属的记录保持不可见，不自动指派给本地用户。
4. 增加 `(identity_id, status)` 索引。
5. 自引用关系使用 `ON DELETE SET NULL`，删除被替换的记录不阻止删除操作。

旧数据不通过模型重新分析，不因升级静默删除或改变其内容。

## 5. 读取与修改边界

仓储接口区分两种行为：

- `list_visible(identity_id)`：读取当前身份的记录及明确共享的记录，默认仅 `active`。
- `get_owned(identity_id, memory_id)`：按记录 ID 和归属身份共同查询，用于修改、删除与查看私有来源。

业务接口必须接收非空身份，缺失时显式失败；聊天记忆子流程记录原因并跳过，不读取全库。全库查询仅作为命名明确的内部迁移/运维接口，不提供给聊天。

共享只授予内容读取能力，不授予修改权或原始消息读取权。非所有者的共享记忆详情仅展示内容和类型，不展示来源消息。自动提取只匹配当前身份拥有的记忆，不能修改其他身份的共享记录；共享记录也不能阻止用户保存自己的同内容记录。

第一版不开放新增共享记忆的产品入口，保留已有 `shared` 兼容行为。

## 6. 提取、校验与提交

### 6.1 输入

提取器接收：

1. 本轮用户消息及其 ID，作为唯一事实依据。
2. 本轮助手回答，仅帮助理解上下文，提示词明确禁止从中推断用户事实。
3. 最近 4 条此前会话消息，用于解释“这个项目”等指代；新的事实断言仍必须得到本轮用户表达支持。
4. 当前身份拥有的有效记忆候选，包含 ID、类型、内容和 `updated_at`。

旧记忆候选取本轮检索结果及最近更新记录，去重后最多 20 条。候选不完整时宁可少更新；第一版不声称能识别任意历史冲突。

### 6.2 输出协议

模型只返回操作数组：

```json
[
  {
    "action": "replace",
    "target_id": "旧记忆 ID",
    "type": "preference",
    "content": "用户已戒咖啡，不希望收到咖啡推荐",
    "evidence": "最近戒咖啡了，以后别推荐"
  }
]
```

| action | 必填信息 | 行为 |
|---|---|---|
| `add` | type、content、evidence | 新增记录 |
| `replace` | target_id、type、content、evidence | 使旧记录被替换并创建新记录 |
| `complete` | target_id、evidence | 完成目标/项目 |
| `invalidate` | target_id、evidence | 使不再成立的旧事实失效 |

没有可靠操作则返回 `[]`。`evidence` 必须是本轮用户消息中的原文片段，不单独存库，可由来源消息核查。它用于限制来源，不能证明语义一定正确。

### 6.3 应用层校验

- 类型仍限于现有六种：profile、preference、goal、fact、relationship、project。
- 内容去空白后不能为空，单条最多 500 字符；单轮最多 10 个操作，超出时拒绝本轮结果并记录原因。
- 修改目标必须存在于传给模型的候选内，属于当前身份，且状态为 `active`。
- `complete` 只允许 goal/project；`replace` 保持原类型。
- 同一目标不能在同一批次被修改两次。
- `evidence` 必须能在本轮用户消息中找到。
- 提取期间目标状态或更新时间已变化，则跳过该目标操作，不覆盖用户刚做的纠正。

非法结构拒绝整批；结构正确但个别目标过时或越界时跳过对应操作，合法操作仍可提交。日志记录操作数量、跳过原因和来源 ID，不输出完整聊天内容。

### 6.4 去重与事务

移除子串去重。新增操作仅对当前身份有效记忆做“相同类型 + 去首尾空白后的内容完全相同”去重。语义重复依赖候选判断，第一版不保证自动合并所有改写。

整批合法操作使用一个事务提交，替换的旧状态和新记录必须一起成功。仓储方法改为 `flush`，由应用服务统一 `commit/rollback`，避免当前逐条提交留下半完成替换。

后台任务调用模型前结束当前数据库事务；得到模型结果后重新读取目标并开启短事务，不在网络等待期间持有写事务。记忆操作与任务完成状态在同一事务提交，失败时统一 rollback，已经完成的聊天不受影响。

取消或失败的回答不创建提取任务。重新生成助手回答不重复提取同一用户消息，任务通过用户消息唯一键保证幂等。

## 7. 用户管理入口

新增 `application/memories.py` 中的 `MemoryService`，CLI 只解析参数和展示结果，身份与事务校验由服务负责。

```bash
zhiyu memory list
zhiyu memory list --all
zhiyu memory search "咖啡"
zhiyu memory show <id>
zhiyu memory add --type preference --content "用户喜欢简洁的回答"
zhiyu memory edit <id> --content "用户喜欢详细解释，并附示例"
zhiyu memory complete <id>
zhiyu memory forget <id>
```

第一版命令默认只管理本地身份，不提供任意 QQ 身份选择参数。`list --all` 展示所有状态；列表包含 ID、类型、状态、内容，详情补充来源、时间和替换关系。

手动添加不调用模型，设 `origin=manual`。手动编辑通过创建替换记录完成，沿用自动替换生命周期；手动操作没有来源消息，详情显示“用户手动操作”。

`forget` 物理删除指定记录，并明确显示删除范围。历史聊天不会同步删除，用户之后再次明确提及同一信息时可能重新提取；本阶段不提供“永久禁止记住某主题”。

交互式聊天增加 `/memory`（列出有效记忆）、`/remember <type> <content>`、`/forget <id>`。手动命令显示确定的成功或失败结果。自然语言中的“记住”仍经自动提取，助手不能在提交前承诺保存成功。自然语言的永久删除留到具备受控操作工具时实现，第一版使用确定的 `/forget` 命令。

## 8. 检索与上下文预算

正确性完成后再调整检索，拆成两部分：

1. **稳定信息**：当前身份的有效 profile/preference，按最近更新时间排序，最多 6 条。
2. **相关信息**：其余有效记忆及可见共享记忆，按查询匹配取最多 5 条。

稳定信息让“给我推荐早餐”也能使用已存饮食偏好，不要求问题中出现原词。两部分按 ID 去重，排除失效、已完成和已替换记录。

字符检索先使用归一化重叠分数：

```text
similarity = |query_bigrams ∩ content_bigrams|
             / sqrt(|query_bigrams| × |content_bigrams|)
score = similarity × (1 + importance)
```

空集合得分为 0。初始相似度门槛为 0.15，最终数值根据固定评估集调整，不作为用户配置项。

长期记忆文本使用总预算：`min(1600, context_window × 4 × 0.1)` 字符；未知模型窗口时用 1600 字符。该估算沿用当前字符预算方式，并非精确 token 计数。优先保留稳定信息，再填相关信息，只纳入完整条目。

输出包含简短编号、类型和内容，并说明“以下为历史用户信息，当前用户的明确纠正优先”。记忆内容按数据处理，不执行其中的指令。

## 9. 会话恢复

`list_goals` 只返回有效 goal/project，欢迎最多展示 3 个，按最近更新时间排序。

`build_recall` 保留最近会话末尾最多 6 条消息，额外限制历史文本 2400 字符；超过时从最旧消息移除，单条仍过长则截断并标识。恢复目标最多 3 条、共 600 字符，避免将全部目标重复注入。

恢复内容和长期记忆按 ID 去重；组装层传递已注入目标 ID，避免使用文本近似去重。最近本地会话查询增加身份过滤，不依赖“所有 local 会话都只有一个身份”的隐含条件。

新会话首轮恢复仍是规则拼接。已完成目标不会出现在事项列表，但真实历史可能提及它；提示词明确事项状态以有效记忆为准。

## 10. 可恢复的异步提取

该阶段使用持久化任务，不以裸 `asyncio.create_task` 作为唯一保障：单条 CLI 即使退出，也能在后续启动时恢复未完成任务。

持久化 `memory_jobs` 记录任务 ID、用户消息 ID（唯一）、助手消息 ID、身份、Provider、模型、状态、尝试次数、最近错误与创建时间。

- 助手消息与任务在同一事务保存；回答 `done` 不等待模型提取。
- 常驻 CLI/QQ Runtime 使用单个消费者处理，模型调用在数据库事务外执行。
- 单条 CLI 返回后保留待处理任务；下次 Runtime 启动或显式 `zhiyu memory sync` 时处理。
- 启动时恢复中断任务；最多尝试 3 次，之后标记失败，允许显式重试。
- 操作提交与任务完成在同一事务落库，避免重启后重复应用。
- 用户删除任务来源消息时取消任务；Provider 不可用时记录失败，不换模型静默重试。
- 该阶段按创建顺序处理任务；用户手动删除、修改记忆前取消该身份未完成任务，防止旧任务重新保存已忘记的事实。用户再次发言后可产生新任务。

后台模式下“已回答”与“记忆已保存”是两件事。CLI 通过 `memory status` 显示任务数量，`memory sync` 恢复并处理任务，`memory retry` 重置失败任务后重试。

## 11. 实施顺序与代码范围

| 阶段 | 主要变更 | 完成检查 |
|---|---|---|
| A：隔离、来源和管理 | models、迁移、仓储、MemoryService、CLI | 升级不丢数据，能查看/纠正/删除，空身份不读全库 |
| B：更新与失效 | extractor、manager、chat 的消息 ID 传递和事务边界、recall 状态过滤 | 改口替换、目标完成、失败回滚 |
| C：检索和预算 | retriever、context、recall | 相关性评估改善，注入量有上限 |
| D：后台处理 | 持久化任务、消费者、sync 入口 | 回答不等待提取，中断可恢复，不重复应用 |

实现只修改记忆相关入口和必要调用者，没有重构角色、渠道或 Agent Runtime。

## 12. 验证与验收

### 12.1 确定性测试

- 身份为空拒绝读取；用户 A 无法修改用户 B 的记录；共享读取不暴露私有来源。
- 替换产生一条有效新记录及一条被替换旧记录；中途失败全部回滚。
- 非目标类型不能完成，完成目标不再进入欢迎和检索。
- 非法 action/type、空内容、伪造 ID、跨身份目标、过期更新时间均被拒绝或跳过。
- 证据不属于本轮用户消息时不能写入。
- 重复新增同内容不产生新记录；否定句不被子串去重吞掉。
- 手动纠正保留替换关系，忘记删除指定记录，删除会话后长期记忆可保留。
- 迁移保留旧内容、身份、共享标记和重要性，补齐默认状态。
- 重新生成、取消、模型输出异常不产生重复或半完成操作。
- 上下文条目不重复，预算生效，历史裁剪行为保持可用。

### 12.2 语义评估

建立至少 30 组固定中文对话样例，覆盖自述、助手建议、引用、改口、并存偏好、目标完成和模糊指代。每组标注允许操作与预期有效记忆。

模型评估与单元测试分开：单元测试验证协议与执行规则；真实模型评估验证提取语义。记录 Provider、模型和提示词版本，避免把 mock 通过当作真实准确率。

验收门槛：

- 确定性测试全部通过。
- 固定评估集中的助手建议、引用和身份隔离样例不能产生错误写入。
- 明确改口与目标完成样例至少 90% 正确，模糊指代不得错误修改其他记忆。
- 检索评估至少包含 20 个带目标记忆的查询；报告 Recall@5、无关记忆比例及同义表达漏召回数。新方案 Recall@5 不低于当前算法，无关记忆比例不升高。

若同义表达仍是主要漏召回来源，再以同一评估集验证 embedding 方案；不直接扩大 top_k 掩盖问题。

### 12.3 实施结果

- DeepSeek `deepseek-chat`、temperature=0：30 组提取样例全部通过，错误写入 0 组。
- 20 组检索样例：当前与原算法 Recall@5 均为 0.95；无关结果比例由 0.1739 降至 0.1364；两者均有 1 组纯同义表达漏召回。
- 评估入口分别为 `scripts/evaluate_memory.py` 和 `scripts/evaluate_memory_retrieval.py`，固定样例保存在 `tests/fixtures/`。

## 13. 取舍与已知限制

- 每轮仍需一次额外模型调用，但由持久化后台任务执行，不阻塞回答完成。
- 来源片段校验能约束输入来源，无法完全阻止模型误解语义；用户管理入口仍是必要闭环。
- 最多 20 条候选无法覆盖所有历史冲突，字符检索也不能保证语义召回。
- 物理忘记指定记录不等于擦除历史聊天，也不阻止未来重新提取；产品反馈必须写明范围。
- 本方案仅按现有身份维度隔离，不新增 QQ 群、Bot 或项目维度，相关需求应在渠道身份设计中单独处理。

本方案完成的标准，是用户能核查与纠正记忆，后续对话只使用有效记录，并且提取任务不阻塞回答、进程中断后可恢复。
