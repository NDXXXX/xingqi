# 架构与信任边界修复设计方案

> 日期：2026-10-07
> 状态：已实施（2026-10-07）
> 依据：根目录 `AGENTS.md`、当前代码与测试；设计文档中的其他规划不视为已实现功能。

## 目标与判断

本方案处理本次核对确认的规则差距：本机 API 的访问检查范围、Skill 元数据的信任层级，以及 API、CLI、TUI、QQ 入口中的业务查询和持久化操作。完成后，入口只负责协议转换和展示，业务规则由 Application 组织；现有记忆恢复、QQ 权限和 MCP 授权行为保持可验证。

这里的“入口直连持久层”指入口自己打开数据库会话、选择 Repository 或执行索引操作。它是职责边界问题，**不代表每个现有调用都已经产生安全漏洞**。只迁移本次定位到的业务访问，不为了让目录图绝对单向而重写运行时。

| 结论 | 项目 | 理由 |
| --- | --- | --- |
| 必须修 | 所有 `/api` 路径的本机访问边界 | 记忆等写接口目前不经过管理路由的 Host/Origin 检查；边界不一致。 |
| 必须修 | Skill 描述进入系统消息 | 可安装 Skill 的描述属于外部内容，不应以系统消息的权限交给模型。 |
| 必须修 | 入口中的会话、记忆、Embedding 和 QQ 群策略访问 | 这些入口直接选择数据库或核心操作，后续规则变更容易遗漏入口。 |
| 必须说明，不做行为迁移 | MCP `legacy_all_tools` | 此字段既保留旧授权，也承载用户当前主动选择的 `--allow-all`；直接清除会撤销已有权限。新服务默认没有工具授权。 |
| 保留 | `MemoryService` 兼容入口、`RuntimeHost` 的渠道组装、渠道媒体存储组件 | 分别承担既有调用兼容、运行时组装和独立媒体存储职责；仅因调用图或类名而搬迁会增加改动与回归风险。 |

## 1. 统一本机 API 边界

执行 [《本机 API 与对话可靠性修复设计方案》](本机API与对话可靠性修复设计方案.md)第 3 节的访问边界设计。本方案只纳入该节；该文档的模型选择和故障切换改动属于独立任务。

- `api/app.py` 对所有 `/api` 请求检查回环连接对端及回环 `Host`，不再按管理路由前缀挑选。写请求统一检查来源，并要求固定的 `X-Zhiyu-Request: 1` 请求头。
- `web/src/api.ts` 及直接使用 `fetch` 的写请求添加该头；更新 README 中本机脚本调用写接口的要求。CLI、TUI、QQ 仍直接调用应用代码。
- 覆盖 Provider、记忆、聊天、运行取消的跨来源写请求，以及记忆和会话的非本机 `Host` 读请求。拒绝后不得产生数据变更；正常本机 Web 流程仍能工作。

这改变本机第三方 HTTP 脚本的写请求格式，必须在 README 明示。固定请求头是浏览器跨站请求防护，不作为用户身份认证。

## 2. 保持 Skill 内容的低信任层级

`integrations/skills/loader.py` 接受非空字符串作为 `description`，`core/agent/context.py` 当前把匹配到的名称和完整描述写入 `role="system"`。描述可能包含换行或指令文本；仅给它加引号仍会把外部内容放在高优先级消息中。

调整 `core/agent/context.py`：继续用名称和描述做匹配，但系统消息只列经过名称格式校验的 Skill 名称，并提示模型需要时调用现有 `read_skill`。完整正文继续作为工具结果返回，不预先提升到系统消息。无需更改 Skill 文件格式、匹配算法或安装流程。

验收：合法 Skill 仍能匹配并被读取；含换行和指令文本的描述不出现在系统消息中；Skill 正文只在调用 `read_skill` 后作为工具结果出现。测试应检查消息角色与实际内容，而不是只检查是否包含某个短语。

## 3. 把入口中的业务访问收回 Application

### 3.1 会话与运行记录

`api/routes/agent.py` 直接查询会话、消息和运行记录；`cli/commands/chat.py` 与 `cli/tui.py` 分别读取聊天历史，CLI 还自行查找本机身份和续接会话。

新增一个职责明确的 `application/conversations.py`，提供会话列表、消息历史、运行详情、运行取消和本机续接快照。它复用现有 Repository、`core.recall` 与运行取消机制，在数据库会话关闭前组装调用方需要的数据。API 保留 HTTP 状态码与 SSE 序列化，CLI/TUI 保留终端格式；三处不再自行打开数据库或重复选择身份。不要为每个查询再建一个 Service、Interface 或 Registry。

验收：API 路径、字段、404 语义、CLI/TUI 的历史与续接显示不变；同一会话在三个入口看到相同消息；API、CLI 聊天命令和 TUI 源码不再直接引用数据库会话或 Repository。

### 3.2 记忆索引与导出

`cli/commands/memories.py` 的 `index` 直接调用核心重建函数，`export` 自行查本机身份并读取 Markdown 文件。让现有 `MemoryService` 提供这两个管理用例：索引仍调用现有 `rebuild_index`，导出只返回当前本机身份可见的文件名与内容。CLI 只解析参数和打印结果。

保留文件 mutation、sync、recovery、身份隔离及当前索引重建顺序；不改 Markdown 格式或数据库 schema。验收包括索引重建后的状态、导出只覆盖本机身份，以及现有 CLI 输出格式。

### 3.3 Embedding 配置

`cli/commands/integrations.py` 的 Embedding 分支直接打开数据库、调用核心配置函数并操作 Keychain。把“查看配置状态”和“保存配置与密钥引用”收进现有 `application/providers.py` 的 Provider 配置用例；具体 Embedding Provider 请求和向量逻辑仍留在 Provider 层。CLI 只负责交互式读取密钥和展示结果。

验收：环境变量引用与 Keychain 两条路径均可配置；CLI 不打印密钥；命令参数、状态文本与现有配置格式保持一致。

### 3.4 QQ 群策略

`channels/qq/adapter.py` 的 `_is_allowed` 直接查询群策略。由现有 `ChannelService` 读取策略并形成允许/拒绝及工具白名单、群提示词的结果；在启动 QQ Adapter 时把这个查询函数注入已有策略阶段，不增加通用策略框架。Adapter 保留主人身份、私聊、@、Token、去重及恢复的执行顺序。

验收：未配置或禁用的群仍被拒绝；仅主人消息可通过；@ 和群工具白名单保持原行为；重连与恢复事件也使用同一策略。Adapter 不再自行创建 Repository 或数据库会话。

## 4. 明确保留的边界

- `channels/media.py` 是集中管理媒体文件和索引的存储组件，并非 API/CLI/QQ 的命令入口。其文件与数据库协调已经集中在一处；本轮不为移动目录而拆开它。
- `application/runtime.py` 是进程组装点，实例化 ChannelManager 和 ChannelRouter；`application/channels.py` 负责渠道配置与启停。现有 Application 与 Channels 在**目录层面**双向引用，但本次未发现必须先解决的 Python 模块循环导入。实施时不得新增反向业务调用；若出现实际循环导入，再按具体调用拆分，不预先建立一套接口层。
- `application/memories.py` 的 `MemoryService` 是已实施的兼容入口，维护同一个 MemoryStore 并统一暴露读写用例。它不是本次新建的空转发层；本方案的索引/导出用例会让入口继续保持单一，现阶段不批量改掉所有调用方。
- `legacy_all_tools` 同时表示历史延续授权和当前用户显式选择的全部工具授权。`cli/commands/integrations.py` 已显示检查提示；本轮保留权限语义和字段，不做无法区分授权来源的静默清零。`AGENTS.md` 应把规则写成“新 MCP 配置默认无工具权限；全部工具权限须由用户明确选择，历史配置保留原授权并提示复核”。若产品决定取消“授权全部工具”，应单独设计用户迁移流程。
- `cli/main.py` 启动时执行日志配置和 Alembic 升级属于进程初始化，不作为业务入口越层访问迁移。

## 5. 实施顺序与完成条件

| 阶段 | 改动 | 验证 |
| --- | --- | --- |
| 1 | 统一 API 边界及前端请求头 | Host/Origin/写请求回归测试；现有 Web API 测试与前端测试。 |
| 2 | Skill 匹配元数据降权 | 含恶意描述的消息角色测试；现有 Skill 和 Agent 上下文测试。 |
| 3 | 会话与记忆入口收口 | API、CLI、TUI、记忆索引/导出及身份隔离测试。 |
| 4 | Embedding 与 QQ 策略收口 | Provider 配置、QQ 权限、去重、恢复和重连测试。 |
| 5 | 更新 `AGENTS.md`、README 中与实际边界有关的文字 | 核对文档、导入关系与完整 CI 检查。 |

每阶段只修改对应调用方和必要测试，不借机改 Provider 故障切换、记忆算法或 QQ 协议。涉及的现有用户数据只通过隔离测试目录验证；不得用真实 `~/.zhiyu/` 做迁移冒烟测试。

完成的可检查条件：

1. 所有 `/api` 读写请求经过同一访问边界；跨来源和非本机 Host 的回归案例被拒绝。
2. Skill 描述不进入系统消息，Skill 仍可按需读取。
3. 上述 API、CLI、TUI、QQ 入口不再直接打开业务数据库会话或执行核心索引操作；启动初始化和专用媒体存储例外有明确职责。
4. 原有 API/CLI/TUI/QQ 行为和记忆一致性测试通过；无新增循环导入或纯转发服务。
5. 执行 `uv run pytest -q`、`npm --prefix web run typecheck`、`npm --prefix web test`、`npm --prefix web run build`、`uv run zhiyu --help`、`uv build`、`git diff --check`，并检查构建产物差异。

实施结果：已按第 1～5 阶段修改运行代码、前端请求、测试、`AGENTS.md` 与 README。会话查询集中于 `application/conversations.py`；记忆索引/导出、Embedding 配置和 QQ 群策略由现有 Application 服务承接。MCP 既有授权语义及第 4 节所述职责边界保留。

验证结果：在临时 `ZHIYU_DATA_DIR` 下，Python 测试 230 项通过；前端类型检查和 6 项测试通过，前端构建、`zhiyu --help`、`uv build`、`git diff --check` 均通过。前端构建更新了受版本管理的 `src/zhiyu/web/static/react/app.js`。未修改数据库 schema，因此无需 Migration。
