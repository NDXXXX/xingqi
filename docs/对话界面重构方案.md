# 对话界面重构方案（Rich TUI）

> 版本：v1.0  
> 日期：2026-09-29  
> 状态：Phase A/C 已实施，Phase B 未开始  
> 定位：把 `zhiyu chat` 从"ANSI 逐行流"重构为 OpenClaw 式现代 TUI  
> 上游文档：[CLI 优先开发设计方案](CLI优先开发设计方案.md)、[CLI 对话交互设计方案](CLI对话交互设计方案.md)  
> 关系：本方案**推翻** [CLI 对话交互设计方案](CLI对话交互设计方案.md) §9 的"不做全屏 TUI"边界，其余（工具卡片、`/verbose`、打印模型）保留并在新 UI 里重新落地。

## 1. 结论

把当前"纯文本提示符 + 逐行打字"的 chat，重构为**现代 TUI 对话界面**，消除机械感：

- **输入**：统一输入控件（prompt_toolkit 或 Textual Input），消灭 `你> 你>` 前缀堆叠，用微提示符 `❯` / `user ❯`。
- **回复**：圆角边框气泡/Panel，Markdown 自动高亮、代码块美化。
- **状态栏**：底部固定 HUD，显示 `idle | generating | tool`、模型、会话、Token 消耗。
- **会话恢复**：启动时读最近会话 + 记忆，列出 2~3 个编号快捷后续行动；开场白直接带上下文，不堆机械套话。
- **异常**：Ctrl+C、子进程异常格式化为告警组件，不裸抛堆栈。

## 2. 现状缺陷（对应代码事实）

| 缺陷 | 根因 | 位置 |
|---|---|---|
| `你> 你>` 前缀堆叠 | 手工 `input("你> ")` 的 prompt 管理与流式输出交错，无统一输入控件 | [main.py](src/zhiyu/cli/main.py) `_chat` |
| `星栖>` 单独占一行、纵向空间低 | 前缀与正文分离打印，无气泡容器 | [main.py](src/zhiyu/cli/main.py) `_send` |
| 无结构化分块 | 只有 ANSI 颜色，无 Panel/Markdown/元信息区 | 全文 |
| 冷启动一句 `星栖 CLI。输入 /help…` | 启动时不读任何历史，无会话恢复 | [main.py](src/zhiyu/cli/main.py) `_chat` 开头 |
| 机械客套回复 | 首 turn 的 system context 无"上次工作"信息 | [context.py](src/zhiyu/core/agent/context.py) |
| Token 无显示 | Provider 从不请求/解析 `usage` | [openai_compatible.py](src/zhiyu/core/providers/openai_compatible.py) |

## 3. 关键决策：库选型

这是整个方案的岔路口，二选一：

### 选项 A：Textual（全屏 TUI 框架）—— 推荐

- 原生支持：底部固定 Footer/HUD、可滚动会话区、输入控件、富文本（内部就是 rich）。
- 与现有 `_send` 异步流式通过 `run_worker` + 消息回传衔接。
- 代价：重写交互循环为 `App` 架构，依赖较大，测试方式改变（`run_test` 驱动）。

### 选项 B：rich + prompt_toolkit（轻量组合）

- rich 负责 Markdown/Panel/状态行，prompt_toolkit 负责输入（历史、编辑、消除前缀 bug）。
- 保留现有 async `_send` 循环基本不动，改动更小、风险更低。
- 代价："状态栏固定 + 会话区滚动"需要手工管理视口，做不到 Textual 那样干净的 sticky HUD，只能做到"每轮底部跟一行元信息 + 输入行底部工具栏"。

**建议选 A**，因为"底部固定状态栏 + 滚动会话 + 输入控件"正是 Textual 的看家场景，选 B 等于用 rich 手工重造一个残缺的 Textual。但 A 是一次较大的结构改动，若想先低风险验证，可先用 B 落地一期。

## 4. 目标界面

```text
╭─────────────────────────────────────────────────────╮
│  你好 zy！上次咱们聊到 Memory 抽取，还没定检索方案。  │  ← 助手气泡（Markdown）
│  想继续的话：                                       │
│    1. 定 Memory 检索策略                             │
│    2. 排查 Provider usage 缺失                       │
│    3. 新建会话                                      │
╰─────────────────────────────────────────────────────╯

❯ 用户输入 ▌                    ← 输入行（微提示符 + 前景色）

idle · deepseek-chat · 会话 #a1b2c3 · tokens 156k/1.0m
```

- 气泡：用户消息与助手消息不同前景色/背景，助手用圆角 Panel。
- 状态行固定底部，随事件流切换 `idle`（等输入）/ `generating`（流式中）/ `tool`（跑工具）。

## 5. 分层与依赖

本方案分三层，**渲染先行，后端与 Agent 行为后续**：

| 层 | 内容 | 依赖 |
|---|---|---|
| A 渲染 | 输入控件、气泡、Markdown、状态栏（idle/generating/tool + 模型 + 会话）、优雅异常 | 无后端改动，可立即做 |
| B 后端埋点 | Token 消耗（Provider 请求 `stream_options.include_usage` 并解析 `usage`）；会话命名（用 title 或短 ID） | 需改 Provider + 事件流 |
| C Agent 行为 | 启动读最近会话 + 记忆，注入首 turn context，生成编号快捷行动 + 简洁开场 | 需改 `with_agent_context` / 新增 recall 服务 |

## 6. 分阶段实施

### Phase A：TUI 外壳（渲染层）

- 按 §3 选定库重写 `_chat` 交互循环；保留 `ChatService.run` 事件流不变，事件分发到 UI 组件。
- 输入控件接 `ChatService` 与斜杠命令（`/new /history /model /character /verbose /tools /clear /exit` 全部平移）。
- 气泡渲染 `chunk`（Markdown），工具卡片沿用 `_tool_lines` 渲染进气泡下方的元信息区。
- 状态栏：`idle`（等输入）→ `generating`（首个 chunk 前）→ `tool`（tool 事件时）→ 回 `idle`；显示模型名与会话短 ID。
- 异常：Ctrl+C（KeyboardInterrupt）、子进程异常（如 `ESRCH`）捕获后渲染为告警面板，不裸抛堆栈。

验收：无 `你> 你>`；气泡/Markdown/代码块正常；状态栏随状态切换；Ctrl+C 不破坏版面；75 项既有测试仍绿。

### Phase B：Token 与会话命名（后端埋点）

- `OpenAICompatibleProvider` 请求时带 `stream_options: {"include_usage": true}`，解析流末 `usage`；`LLMResponse` 增 `usage` 字段；运行时把 usage 塞进事件流。
- 状态栏显示 `tokens N` 与占比（上限来自上下文窗口或固定演示值）。
- 会话命名：显示 `title`（截断）或 `#短ID`。

验收：真实对话后状态栏出现 token 数；切换模型后显示对应模型名。

### Phase C：会话恢复与开场（Agent 行为）

- 新增 recall：启动时读最近一条本地会话的尾部消息 + `MemoryRepository.list(identity)`，用 LLM 或规则生成"上次聊到 + 2~3 个编号后续行动"。
- `with_agent_context` 注入该 recall 作为首 turn system 内容；开场白据此生成，去掉机械套话。
- 编号行动可输入数字直接续作（如 `1` = 发送预置续作指令）。

验收：重启 chat 后开场带上次上下文；选编号能续上话题；无历史时优雅降级为简短普通开场。

## 7. 测试策略

| 层 | 覆盖 |
|---|---|
| 渲染组件 | 工具卡片/气泡渲染逻辑保持纯函数（沿用 `_tool_lines` 测试）；TUI 用库自带测试驱动（Textual `run_test` 或 prompt_toolkit 单测） |
| 状态机 | idle/generating/tool 转换用纯函数测，不依赖真实 TTY |
| Provider usage | mock 含 `usage` 的流，断言 `LLMResponse.usage` 解析正确 |
| recall | mock 最近会话 + 记忆，断言注入内容与编号行动格式 |
| 回归 | 既有 75 项测试全绿；非 TTY 路径（`zhiyu chat "消息"`）输出保持纯文本不破坏 |

TUI 的可测性是选库时的重要考量：Textual 有官方 `run_test` 测试驱动，prompt_toolkit 输入可单测。两条路线都能测，但 Textual 的整体行为测试更完整。

## 8. 验收标准

1. 交互模式下无 `你> 你>` 前缀堆叠；输入有历史与编辑能力。
2. 助手回复以气泡/Panel 呈现，Markdown 与代码块高亮正确。
3. 底部状态栏随 idle/generating/tool 切换，显示模型与 token。
4. Ctrl+C、子进程异常渲染为告警面板，不裸抛堆栈、不破坏版面。
5. 重启后开场带上次会话上下文与 2~3 个编号行动；无历史时降级为简短开场。
6. 单条模式 `zhiyu chat "消息"` 仍输出干净纯文本。
7. `uv run pytest -q` 全绿。

## 9. 范围边界

| 不做 | 理由 |
|---|---|
| 多窗格（会话列表侧栏 + 聊天区并排） | 单会话足够，侧栏留待 Web UI 阶段 |
| 鼠标点击气泡、拖动、富文本复制 | 终端交互仍以键盘为主 |
| 真正的"未完成事项"追踪（todo 数据模型） | 用 memory 的 goal/project 类型近似即可，不新建 todo 系统 |
| 向量检索替换 bigram 检索 | 与本方案无关，另行规划 |
| 多模型并排对比 | 超出对话界面范围 |

## 11. 实施记录

### Phase A（已实施，2026-09-29）

- 依赖新增 `textual==8.2.8`。
- 新增 [tui.py](../src/zhiyu/cli/tui.py)：`ChatApp` 包含可滚动会话区、底部状态栏（`idle | generating | tool` + 模型 + 会话短 ID）、`Input` 输入控件。
- 斜杠命令（`/new /history /model /character /verbose /tools /clear /exit`）全部平移为 TUI 动作；工具卡片沿用 `_tool_lines` 渲染为 dim/red 富文本。
- `main.py`：`_chat` 改名 `_chat_line` 保留为**非 TTY 回退**（管道/CI），新增 `_chat_tui` 分发。TTY 且无单条消息时进 TUI，否则走行模式。单条消息模式（`zhiyu chat "消息"`）仍输出干净纯文本。
- 异常：流式 worker 内 `except Exception` 渲染为「运行失败」消息，不裸抛堆栈。

验收结果：78 项测试全绿（新增 3 项 TUI 测试，`run_test` 无头驱动验证 compose / 命令挂载 / 流式挂载）。非 TTY 回退与单条模式实测正常。

**未验证项**：TUI 在真实 TTY 下的视觉效果（颜色、边框、气泡）无法在本环境无头验证，需在终端 `uv run zhiyu chat` 人工确认。视觉样式（§4 的圆角边框、柔和背景）为最小实现，待迭代。

### Phase C（已实施，2026-09-29，二次修订）

- **默认续接**：`zhiyu chat` 无 `--conversation` 时，自动续接最近一条有消息的本地会话（`last_local_conversation`），不再默认新建会话。续接用真实历史，避免标题套娃。
- 新增 [recall.py](../src/zhiyu/core/recall.py)：`last_local_conversation`（默认续接）、`list_goals`（goal/project 记忆作为"进行中事项"）、`build_recall`（fresh 会话首 turn 注入上下文，规则版不调 LLM）、`format_welcome`。
- `with_agent_context` 增 `recall` 参数，作为首个 system 块注入（标注"用于衔接上下文，不要逐字复述"）。仅在真正新开会话（显式 `/new` 或无历史）时生效。
- 启动欢迎：续接时显示「已继续上次对话「X」」；有进行中事项时附编号「跟进」行动，首个 turn 输入纯数字映射到对应事项。
- `main.py` 抽 `_entry_state(args)` 统一解析启动状态（TUI 与 line 模式共用，便于测试注入）。

验收结果：89 项测试全绿。真实对话验证：`zhiyu chat` 续接最近会话（会话数不变、追加消息），无标题套娃。

**偏离与限制**：续接用**真实会话历史**（不是 LLM 摘要）；"进行中事项"来自 goal/project 记忆，若 LLM 提取器没存过这类记忆则欢迎不显示编号行动。若需"上次聊到 X、还没做完 Y"的提炼式摘要，需额外 LLM 调用，属后续增强。
