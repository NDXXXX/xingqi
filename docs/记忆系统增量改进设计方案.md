# 记忆系统增量改进设计方案

> 版本：v1.1
> 日期：2026-10-07
> 状态：阶段性实施完成（90 天规则已落地；规模测试与索引陈旧诊断仍待补）
> 范围：长期记忆的写入、晋升、检索，以及长会话上下文压缩
> 前置文档：[OpenClaw 式文件记忆系统重构设计方案](OpenClaw式文件记忆系统重构设计方案.md)、[单机个人 Agent 多 Session 共享记忆设计方案](单机个人Agent多Session共享记忆设计方案.md)

## 1. 结论

星栖已经有 Markdown 记忆文件、SQLite 索引、来源关系、情景记忆和后台巩固，不需要重建一套记忆系统。下一步先补完整**记忆沉淀闭环**，再让索引和会话摘要按变更增量更新。

实施顺序：

1. 将“对话观察 → 等待/复核 → 核心记忆 → 来源归档”设计成完整沉淀生命周期，明确候选何时重试、何时晋升、如何合并和纠正。
2. 晋升后的情景记忆只作为来源证据保留，不再作为普通回答的独立候选；默认回答只自动注入受信任的核心记忆。
3. 聊天路径不再每轮扫描全部 Markdown；程序写入即时更新对应条目，外部编辑只重建变化的文档。
4. 会话摘要成为真正的上下文检查点；后续请求只读取摘要后的消息，压缩时增量推进检查点。
5. 在真实规模的会话和记忆数据上验收召回正确性、延迟与故障恢复。

这份文档是对前置设计**已实施部分的补强**。前置文档中尚未落地的独立功能，例如完整 FTS 文档索引，不因本文被视为已经完成。

## 2. 对照与现状

对照对象是 OpenClaw 当前默认的 **Memory Core**，不是所有可选记忆插件。其官方文档描述了：`USER.md`/`MEMORY.md` 是受预算约束的精选记忆，日记和会话记录是按需检索的情景层；晋升会合并重复内容并保留来源；文件变化触发增量索引；长会话压缩将摘要保存到会话记录并保留最近消息。参见 [Memory architecture](https://docs.openclaw.ai/concepts/memory-architecture)、[Builtin memory engine](https://docs.openclaw.ai/concepts/memory-builtin)、[Compaction](https://docs.openclaw.ai/concepts/compaction)。这些是设计参考，不要求星栖复制其插件体系或所有实现细节。

| 环节 | 星栖当前代码 | 应改进的行为 |
|---|---|---|
| 对话记录 | `messages` 表保存每条会话的原始消息；每轮从会话起点读取 | 原始记录继续完整保存，但模型上下文只读取摘要检查点之后的消息 |
| 记忆提取 | 成功回复后，后台模型从本轮用户原文提取最多 5 条观察，写入 daily Markdown 和索引 | 保留证据约束；重复观察仍可记录为独立来源，但不能在回答里重复表达同一事实 |
| 记忆晋升 | 情景候选晋升为核心时，设置 `promotion_status=promoted` 和 `promoted_to_id`，来源仍为 `status=active` | 保留来源文件和关系；统一过滤晋升来源的普通检索与默认列表 |
| 普通召回 | 核心和所有 active 情景条目一起参加每轮检索；部分 profile/preference 预注入 | 只自动注入有效核心；情景层通过明确历史问题或用户主动检索进入回答 |
| 索引同步 | 聊天准备和后台提取前调用 `rebuild_index`；该函数逐文件读取并更新条目 | 启动恢复与外部编辑按需同步；程序写入即时更新受影响条目；不在每轮聊天全量重建 |
| 长会话 | 全部消息读出后确定性截取旧消息，摘要写入 `conversation_summaries`，下轮不读取 | 摘要记录已覆盖的消息边界；下轮从该边界之后读取并增量压缩 |

核对位置：[chat.py](../src/zhiyu/application/chat.py)、[memory_jobs.py](../src/zhiyu/application/memory_jobs.py)、[context.py](../src/zhiyu/core/agent/context.py)、[consolidation.py](../src/zhiyu/core/memory/consolidation.py)、[indexer.py](../src/zhiyu/core/memory/indexer.py)、[conversation_summary_repository.py](../src/zhiyu/infrastructure/database/repositories/conversation_summary_repository.py)。

### 当前已有的沉淀能力

星栖不是完全没有记忆沉淀：成功对话后，后台提取器把有用户原文证据的观察写入 daily 文件；待处理候选达到 20 条、最早候选超过 24 小时或手动触发时会运行巩固；至少通过主人信任、3 个不同查询召回、活跃项目/目标被提及、或独立重复观察之一后，才交给模型在候选范围内决定合并、替换或忽略。接受的结果写进核心文件并建立来源关系。

目前的不足是：模型的 `ignore` 会把候选永久改为 `rejected`，后续相同事实的新观察无法借用这条旧证据；沉淀结果虽有数据库运行记录和 `DREAMS.md` 摘要，但缺少面向用户的候选状态、具体变更内容和低信心复核入口；巩固运行时还会全量重建索引。本文将沉淀明确列为第一阶段，补上候选可重评、证据链和用户可见性。

## 3. 数据边界

| 数据 | 保留位置 | 用途 |
|---|---|---|
| 完整原始对话 | SQLite `messages` | 查看历史、遗忘、追溯来源；不能跨 Session 自动拼接进当前上下文 |
| 长会话摘要 | SQLite `conversation_summaries` | 当前 Session 的派生上下文检查点，可失效重建；不属于跨 Session 长期记忆 |
| 稳定用户偏好和事实 | 身份 vault 的 `USER.md`、`MEMORY.md` | 默认回答的受预算约束核心记忆 |
| 未晋升观察 | 身份 vault 的 `daily/*.md` | 来源证据、明确历史检索、后台巩固 |
| 信任、来源、生命周期、检索缓存 | SQLite | 决定可见性和可恢复性；不能由 Markdown 正文自行声明 |

继续保持**一个本机 Agent 记忆空间，多条独立 Session**。QQ 主人会话和本机会话共享获准的核心记忆，但普通上下文只使用当前会话的消息。历史消息、日记和摘要都不能通过文本内容提高自己的可信级别。

## 4. 设计 A：修正记忆生命周期与召回

### 4.1 读取规则

增加统一的读取语义，由仓储或专门的候选查询函数承载，避免 API、Agent、CLI 各写一套过滤条件：

| 场景 | 可读取的数据 |
|---|---|
| 普通回答的预注入和快速召回 | `status=active` 且通过现有来源信任规则的核心记忆；仍受身份、相关度和上下文预算限制 |
| 明确问“以前说过什么”的深度召回 | 相关的未晋升情景记忆及当前 Session 原始历史；已晋升来源只可作为核心记忆的证据返回，不能再作为一条并列事实注入 |
| 记忆管理页默认列表 | 有效核心与未晋升情景观察；已晋升来源收在核心记忆的“来源”详情中 |
| 审计、遗忘和历史查看 | 全部状态及来源关系；允许查看已晋升的原始观察 |
| 后台巩固 | 仅 `status=active` 且 `promotion_status=pending`、通过现有信任门槛的情景候选 |

`promotion_status=promoted` 不能简单改成 `status=forgotten`：它仍是核心记忆的来源。保留 `promoted_to_id`、`MemorySource` 和 daily 文件，防止遗忘唯一来源时失去级联依据。`rejected` 表示“不适合晋升为核心”，不等于原话虚假；它也不参与普通自动注入，但可在审计和明确历史检索中查看。

为避免一次对话重复写入造成的噪声，检索结果还应按有效核心 ID 分组：同一核心及其来源只显示核心一次；多个尚未晋升、语义接近的观察可在展示层合并，但各自的来源与时间仍单独保存。不要仅凭模糊相似度在写入时删除观察，因为“重复出现”本身是晋升证据。

### 4.2 冲突与纠正

用户当前消息中的明确纠正优先于旧记忆。已经有明确纠正路径和 `superseded` 状态，本阶段补齐回归用例：旧核心被替换后不进入普通回答；历史问题可按时间找到旧说法并标注“过去”；被遗忘的来源不能通过重建索引重新进入检索。

### 4.3 回填

部署时**不删除任何 daily 文件或旧消息**。对现有 `promotion_status=promoted` 的条目验证 `promoted_to_id` 与 `MemorySource` 是否指向同一身份的有效核心。关系完整的条目立即按新读取规则隐藏；关系异常的条目进入诊断清单，先不自动删除或改写正文。重复执行回填必须得到相同结果。

### 4.4 记忆沉淀闭环

沉淀应是后台逐步筛选、合并和更新用户模型的过程，而不是“提取到一条就算长期记忆”。流程固定为：

```text
当前用户原文
  → 带消息来源的情景观察（pending）
  → 后台确定性资格门槛
  → 模型在限定候选中合并 / 替换 / 暂缓
  → 核心记忆更新 + 来源关联 + 可查看的变更记录
```

规则：

1. **只从用户证据提取。** 继续使用 `evidence` 必须是本轮用户原文子串的校验；助手回答、工具结果和召回出的旧记忆不能成为新事实的独立来源。
2. **情景记录是证据，不直接等于稳定画像。** 一次性信息留在 daily；核心晋升继续使用代码门槛，再让模型判断事实是否稳定、是否应与现有核心合并或替换。
3. **重复证据按来源独立性计算。** 同一条消息、同一事件重试、重复投递不能当成多次独立观察；按不同 `source_message_id` 计数，并展示日期/会话来源。主人直接明确“记住”可作为显式确认路径，仍需保留来源。
4. **暂缓不等于永久拒绝。** 将巩固器的 `ignore` 语义改为 `deferred`：不进入普通注入，也不反复占用每次巩固批次；出现新的独立相关观察时，将相关暂缓证据重新开放评估。只有用户明确删除/纠正，或系统确认内容不应记忆时才永久拒绝或删除。迁移旧 `rejected` 时不自动恢复，避免把旧结论悄悄改回候选；新证据到达后才按规则重开。
5. **沉淀必须能解释。** 每条核心记忆可查看它合并了哪些情景观察、来源会话和时间；每次巩固记录决策（晋升、替换、暂缓）、前后内容和原因。失败或模型输出不合规时不改文件、不改变候选状态，记录失败后可重试。
6. **冲突通过替换而不是追加解决。** 新观察与核心事实相反时，只有确定性关联门槛和受约束的模型判断都通过才 `supersede`；旧条目保留为有时间范围的历史来源，不作为当前事实回答。
7. **让用户纠错。** 记忆页按“核心 / 待沉淀 / 暂缓 / 历史来源”展示状态；用户可编辑核心、明确保留或删除候选。用户操作走现有 Mutation Journal 和遗忘谱系，保证文件与索引一致。

建议的状态变化：

| 当前状态 | 事件 | 新状态 | 普通回答可见 |
|---|---|---|---|
| 新观察 `pending` | 门槛未通过 | `pending` | 否；仅显式历史召回 |
| 新观察 `pending` | 巩固认为证据不足 | `deferred` | 否；仅显式历史召回 |
| `deferred` | 新的独立相关观察到达 | `pending` | 否；重新等待门槛 |
| `pending` | 新建或合并核心成功 | `promoted`，关联 `promoted_to_id` | 只显示核心一次 |
| 核心记忆 active | 新证据确认事实已变化 | 旧核心 `superseded`，创建替代核心 | 只显示当前核心 |
| 任意可管理记忆 | 用户明确删除 | 删除/遗忘并执行来源级联 | 否 |

`deferred` 是产品语义，不新增第二套记忆正文。实现可在 `promotion_status` 增加该枚举值，并在产生新观察时重开相关候选；是否需要 `next_review_at` 等额外字段由实施阶段的状态迁移测试决定，不预先增加。

### 4.5 明确指令、时效和敏感信息

**明确“记住”**：用户直接要求记住一条事实或偏好，视为主人确认，跳过重复次数和召回次数门槛，直接写入对应核心文件；仍要求内容能从用户原文取证、保留消息来源，并走 Mutation Journal。若与一条核心记忆明确冲突，按纠正流程替换；若匹配到多个可能目标，不自动改写旧核心，先保留为待处理并向用户说明。

**时效信息**：所有自动记忆继续保存 `observed_at`。偏好和稳定资料不因时间经过自动删除；goal/project 等进行中事项从最后一次用户明确提及或确认的时间起计时，连续 90 天没有新的用户证据时标记为“待确认”。保留原记忆，不自动删除或续期；回答当前状态问题时说明它是过去提过的计划，不能表述为确定的当前状态。用户再次确认或提供进展后重置 90 天计时并恢复 active；用户表示已完成或取消时按现有生命周期收尾。该 90 天期限由用户确认。

**敏感信息**：自动提取不得保存密码、API Key、验证码、支付凭据等可直接用于访问账户的秘密，也不得把对第三方的敏感个人信息写入长期核心。若用户明确要求记住这类信息，系统应拒绝将秘密写入普通 Markdown 记忆，并提示使用专门的密码管理工具；其他高敏感个人事实即使用户原文出现，也应默认不自动提取，只有用户明确要求时才单独确认保存。

历史 `rejected` 记录不因版本升级自动恢复。出现新的、不同消息来源的相关观察时，系统才把相似旧记录重新设为 `pending`，保留其原始时间和来源，不伪装成新观察；新旧消息仍分别作为独立证据参与资格门槛。

## 5. 设计 B：增量索引与恢复

### 5.1 正常写入

现有 `FileMutationManager` 和 mutation journal 保留。程序追加、替换、删除一个记忆条目后，只更新对应的 `Memory` 索引记录和 embedding 状态；已经完成的文件操作不要求下轮聊天重新遍历所有文件。聊天路径移除无条件 `rebuild_index`；后台提取路径也移除同样的调用。

### 5.2 外部文件编辑与启动恢复

用身份范围内的文档路径、文件大小、修改时间及内容哈希判断哪些文件发生变化。未变化的文件不解析条目、不更新数据库行；变化文件按现有稳定 `entry_key` 规则执行差量 upsert/delete。文件监听或定期轻量检查负责发现手工编辑；应用启动时先恢复未完成 mutation，再对受管文件做一次一致性检查。用户通过 CLI 显式执行的全量重建仍保留为修复手段。

索引检查出错时，聊天继续使用上次有效索引，并在诊断状态中标为 stale/failed。不能在恢复失败后静默将旧索引认定为最新。手工改动 Markdown 不得继承旧条目的来源可信度，遗忘墓碑继续阻止被删除来源重新进入活动记忆。

### 5.3 边界

本阶段只优化当前的 Markdown 条目索引链路。是否引入完整 FTS5、分块索引或常驻文件监听器，应由规模测试决定；这些能力在旧方案中出现过，但当前实现情况须单独验收，不能仅靠文档状态认定已上线。

## 6. 设计 C：会话摘要检查点

### 6.1 摘要的含义

`conversation_summaries` 改为保存“已压缩前缀的摘要”和“该前缀最后一条消息的稳定 ID”。模型输入按以下顺序组装：当前角色与核心记忆、有效的旧摘要、摘要边界后的最近完整对话轮次、当前用户消息。摘要只概括当前会话，不能写入 `USER.md`/`MEMORY.md`，也不能给其他 Session 读取。

当前 `source_message_count` 可继续用于统计，但不能单独充当边界：删除、重新生成或同一时间戳的消息都可能让数量与具体内容不一致。查询顺序固定为 `(created_at, id)`，摘要边界用 `last_message_id` 和对应排序键保存。

### 6.2 增量推进

正常轮次只从边界之后分页读取有上限的消息。如果“摘要 + 新消息”接近模型上下文预算，就把最早的完整轮次并入摘要，原始消息仍留在 `messages` 表。摘要写入与边界推进必须在同一数据库事务内完成；失败时仍使用旧摘要和未压缩的尾部，必要时进行一次确定性压缩以保证本轮可回答。

第一阶段可复用现有确定性摘要逻辑来验证检查点语义。随后只在跨过压缩阈值时调用一次模型生成语义摘要，要求保留未完成请求、明确纠正、姓名/日期/编号等精确信息，并验证长度和来源；验证失败退回确定性压缩。不能每轮重新总结整个会话。

### 6.3 失效条件

重新生成回答、编辑或删除历史消息、遗忘会话来源时，若影响到摘要覆盖区间，必须使该会话摘要失效并从尚存原始消息重建。删除整个会话时通过外键级联清除摘要。版本升级改变摘要格式时，旧摘要可读但不作为新格式继续增量推进；按需重建。任何重建只作用于当前 Session。

## 7. 实施阶段与验收

### 阶段 1：记忆沉淀、生命周期和读取规则

涉及 `core/agent/context.py`、`application/memories.py`、`core/memory/consolidation.py`、`infrastructure/database/repositories/memory_repository.py` 及相关 API/CLI 展示。先补测试，再改读取路径。

验收：用户消息提取出的候选保留来源；重复投递不会增加独立证据数；一次性信息不晋升；同一稳定事实的多条观察合并为一个核心，并能查看来源；暂缓候选在新独立证据到达后可重新评估；明确“记住”可直接写入核心且来源可追溯；API Key 等秘密不进入记忆；goal/project 在 89 天仍保持 active，满 90 天转为“待确认”，新确认后重新计时，且待确认事项不会被回答成当前事实；失败重试不重复写核心或来源；核心替换、用户纠错、遗忘唯一来源和保留多来源核心均有回归覆盖；晋升前的观察可通过明确历史问题找到，晋升后普通回答和默认列表只出现一条核心事实。

沉淀的可观察性也属于验收：用户能看到最近一次运行时间、候选数、晋升/替换/暂缓数量及失败原因；不能只在日志或 `DREAMS.md` 里留下机器可读痕迹。

### 阶段 2：索引路径

涉及 `core/memory/indexer.py`、`core/memory/mutations.py`、`application/chat.py`、`application/memory_jobs.py`、启动恢复与诊断。先记录现状的文件数、条目数、每轮索引耗时，再移除热路径全量调用。

验收：连续发送两条消息且文件未变化时，第二轮不解析任何记忆文件；外部编辑单个文件只更新该文件；中断发生在文件操作与索引提交之间，重启后仍可恢复且不重复；索引不可用时聊天可继续并明确报告索引陈旧。

### 阶段 3：上下文检查点

涉及 `conversation_summaries` 迁移、`MessageRepository` 的边界查询、`core/agent/context.py` 和重新生成/删除入口。旧摘要没有可靠边界，迁移时保留原始消息并将旧摘要标为失效，首次需要时重建。

验收：长会话第二轮以后不再从第一条消息读取全部历史；摘要只覆盖完整轮次且边界不重叠、不遗漏；重新生成、删除、遗忘后不使用失效摘要；同一会话连续压缩多次仍保留进行中的事项；新 Session 不继承旧 Session 摘要。

### 阶段 4：质量与规模验证

用隔离数据库构造 1,000 和 10,000 条记忆、长会话多轮压缩、重复事实、冲突纠正、跨 Session 查询与遗忘场景。记录召回命中、错误注入、每轮文件解析数量、上下文查询行数和 p95 准备耗时。先测旧实现作为基线，再对照新实现；验收条件是功能用例全部通过、普通未变更轮次的文件解析数为 0、长会话正常轮次的历史读取行数有固定上限，且 p95 准备耗时不高于基线。不得用“单次跑通”替代多轮回归。

## 8. 不在本次范围

- 不改变本机与获准 QQ Session 的共享记忆身份规则。
- 不自动合并旧 QQ 身份的历史记忆。
- 不新增多用户权限系统或跨 Session 原始对话自动注入。
- 不迁移到另一种数据库，也不批量删除已有记忆。
- 不为记忆能力重做整套 WebUI；只调整列表与来源详情需要的字段和展示。

## 9. 完成定义

用户说过的内容仍可追溯；稳定事实在普通回答里只出现一次；明确问过去时能找到有来源的旧记录；长会话不会每轮重新处理全部历史；聊天不会每轮重新扫描全部记忆文件。上述行为在本机和获准 QQ Session 上一致，并通过自动化回归与规模测试。

## 10. 本轮实施记录（2026-10-07）

已落地：

- 新增数据库迁移：记录目标/项目最后证据时间、会话摘要消息边界、记忆文件索引快照和巩固决策详情。
