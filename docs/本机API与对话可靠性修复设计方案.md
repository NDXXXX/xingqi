# 本机 API 与对话可靠性修复设计方案

> 版本：v1.0
> 日期：2026-10-07
> 状态：待实施

## 1. 背景与目标

本方案处理 2026-10-07 项目评估确认的三个问题：

1. Web API 的校验只覆盖部分管理写接口。带外站 `Origin` 的简单 POST 可以确认目标记忆；带非本机 `Host` 的 GET 可以读取记忆列表。后者在具备 DNS 重绑定等条件时会扩大数据暴露风险。
2. 新对话先提交会话，再选择模型。没有可用 Provider 时，对话失败但会话列表留下空记录。
3. Provider 故障切换只替换 Provider 和模型名，继续使用主模型的工具、流式及输出上限配置；备用模型的上下文窗口也没有进入兼容性判断。

成功标准是：所有本机 API 都受到一致的访问边界保护；模型选择失败不产生新会话；实际请求始终遵守当前候选模型的能力与限制。保持现有 CLI、TUI、QQ 和 Web 对话事件格式。

## 2. 范围与取舍

- Web UI 仍由 `zhiyu serve` 绑定回环地址，API 仍定位为同机接口；不引入账号、登录或远程访问模式。
- 不改变数据库 schema、记忆文件格式、Provider 配置格式及故障切换顺序。
- 不清理历史上已经产生的空会话；自动删除需要先判定它们是否由其他入口有意创建。
- 不把整个聊天流程改为单一事务。模型请求失败后保留已提交的用户消息与运行记录，便于排查和重试。本轮只消除模型选择失败造成的新空会话。
- 访问检查约束浏览器和网络入口，不把本机其他进程视为不可信主体；拥有用户进程权限的本机程序仍可调用本机 API。

## 3. 本机 API 访问边界

### 3.1 统一规则

在 `api/app.py` 中用一处中间件覆盖**所有** `/api` 路径，代替按管理路由前缀枚举。检查顺序如下：

| 请求 | 检查 | 不满足时 |
|---|---|---|
| 所有 `/api` 请求，包括 GET、HEAD、OPTIONS | `Host` 必须是 `localhost` 或回环 IP，端口必须合法；连接对端也必须是回环地址 | 403 |
| POST、PUT、PATCH、DELETE | 若有 `Origin`，必须与请求的 scheme、Host 和端口一致；否则若有 `Referer`，其来源必须一致 | 403 |
| POST、PUT、PATCH、DELETE | 必须带固定请求头 `X-Zhiyu-Request: 1` | 403 |

浏览器跨站表单不能设置自定义请求头；跨站脚本设置该头会触发预检，服务端不提供跨站 CORS 授权。`Host` 检查阻断通过非本机域名访问本机 API 的路径。自定义头是跨站请求防护，**不是身份认证**；同机 HTTP 客户端可以显式添加该头。

无 `Origin` 和 `Referer` 的本机脚本调用在满足回环对端、回环 `Host` 和固定请求头时允许。无效或 `null` 的 `Origin` 不降级为无来源请求。来源比较使用解析后的 scheme、主机和有效端口，拒绝含用户信息、无效端口或无法解析的值；不信任 `X-Forwarded-Host` 等代理头。静态资源请求仍可正常加载，但不应因此获得 `/api` 例外。

### 3.2 客户端与兼容性

- `web/src/api.ts` 的写请求统一添加固定请求头；`useChatSession.ts` 中直接调用 `fetch('/api/chat')`、`MemoryPage.tsx` 中直接调用 `fetch` 删除记忆的地方也添加该头。
- CLI、TUI、QQ 目前直接调用应用服务，不走该 HTTP API，无需修改。
- 第三方本机 HTTP 脚本在升级后需为写请求增加请求头；在 README 的 Web/API 说明中记录这一点。GET 不需要该头。
- Web API 测试使用回环 `Host`，保留测试客户端的模拟对端处理，不在生产路径放行任意域名。

### 3.3 验收用例

在 `tests/test_web_api.py` 增加参数化测试，至少覆盖：

1. 外站 `Origin` 的记忆确认、对话发送、运行取消及 Provider 写入均返回 403，且无数据变化。
2. 本机 `Host` 搭配非回环连接对端、非本机 `Host` 搭配本机连接对端时，读取记忆和会话均返回 403。
3. 本机来源但缺少固定请求头的写请求返回 403；带请求头的现有 Web 写流程正常。
4. 无 `Origin` 的本机脚本请求在满足其他条件时可写；错误来源、`Origin: null` 和来源端口不一致时拒绝。
5. 静态页面与资源仍返回成功；错误请求返回 JSON 403，不产生模型调用或记忆变更。

## 4. 新会话创建时机

`ChatService._prepare()` 当前在新会话分支调用 `ConversationRepository.create()`，该方法立即提交；随后才调用 `select_provider_model()`。调整为：

1. 先验证渠道权限，查找已有会话并确定 identity。已有会话沿用当前选择优先级。
2. 对尚不存在的会话，构造**不加入 Session、也不提交**的临时 `Conversation` ORM 实例，填入选择模型需要的 `channel`、`identity_id` 和其他相关字段。
3. 用该对象执行 `select_provider_model()`。若无可用 Provider、指定模型不可用或 Provider 没有启用模型，直接报错，数据库中不出现新会话或新消息。
4. 选型成功后才按现有仓储路径创建真实会话；继续准备用户消息、上下文和 Agent Run。现有会话的模型选择失败不改变该会话的消息列表。

不把 `ConversationRepository.create()` 改为全局延迟提交，以免影响 QQ 显式新建 Session 等其他用例。identity 的既有创建行为保持；验收只要求失败时不新增 `Conversation`、`Message` 和 `AgentRun`。

在 `tests/test_chat_service.py` 或 `tests/test_web_api.py` 用隔离数据库覆盖：无 Provider、全部停用、指定 Provider/模型无效、正常新对话、已有对话五种情况。无 Provider 的 Web SSE 仍沿用现有 `error` 事件格式，但会话列表不能新增记录。

## 5. 按候选模型执行故障切换

### 5.1 候选模型数据

`ChatService` 为主模型与每个备用模型准备同一组运行属性：Provider ID、Provider 实例、模型名、`supports_tools`、`supports_streaming`、`supports_vision`、`context_window`、`max_output_tokens`。用一个小的不可变数据结构传给 Agent Runtime，替代目前只包含三项的备用模型元组。该结构仅表达一次请求的候选模型，不增加持久化配置。

保持已配置的 Provider 顺序；每个 Provider 继续按当前规则选择首个启用模型。视觉输入仍要求备用模型支持视觉。对于不符合当前对话要求的候选，复用现有 `step` 事件记录跳过原因并尝试下一个候选；不要静默向其发送不兼容请求。

### 5.2 执行规则

- **工具：**每次调用按当前候选的 `supports_tools` 决定是否发送工具定义。若本轮已经产生工具调用及结果，跳过不支持工具的后续候选，避免把工具历史交给不兼容模型。在首轮尚无工具历史时，允许无工具备用模型直接给出文本答复。执行工具调用的判断也跟随实际响应的候选模型。
- **流式：**调用方要求流式展示时，仅对支持流式的当前候选使用 Provider 流；不支持者使用非流式调用，并按现有协议补发单个 `chunk`。CLI/TUI/Web 无需识别新的事件类型。
- **输出上限：**向每个候选传其自身的 `max_output_tokens`，不沿用主模型值。
- **上下文窗口：**主模型仍按现有逻辑构建和压缩上下文。切到配置了更小窗口的备用模型前，按现有字符预算估算当前消息加该模型的输出预留。能完整容纳则尝试；超出时仅丢弃完整的旧对话轮次，保留系统消息、当前用户消息及完整工具调用/结果配对。若这些必需内容仍放不下，跳过该候选并记录原因。窗口未配置时不声称已验证容量，仍可按现有行为尝试。
- **重试与审计：**现有“可重试错误重试一次、再按顺序切换”的规则不变；`AgentRun` 和记忆任务继续记录最终实际使用的 Provider、模型与 usage。备用模型切换后若再次进入工具轮次，继续使用该候选的能力参数。

上述上下文处理只影响发给备用模型的临时消息副本，不覆盖数据库中的消息或已保存的会话摘要。若已向用户输出文本，继续沿用现有规则，不再切换 Provider，以免出现两份回答拼接。

### 5.3 验收用例

在 `tests/test_agent.py` 和 `tests/test_chat_service.py` 覆盖：

1. 主模型不可用、备用模型禁用工具与流式时，备用请求不含 tools，使用非流式调用，Web/CLI 仍收到正文 `chunk`。
2. 主备输出上限不同，备用请求携带备用模型的值。
3. 备用窗口较小时，只裁掉完整旧轮次；必需的系统消息、最新用户消息或工具配对无法容纳时跳过，并继续尝试下一个候选。
4. 工具结果之后的故障切换不选无工具候选；首轮无工具历史时可选它。
5. 最终 `AgentRun`、`done` 事件和记忆任务使用实际成功的 Provider 与模型；现有重试、流式中途失败不切换等行为保持。
